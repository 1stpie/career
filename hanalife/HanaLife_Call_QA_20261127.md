## 1. 경험 질문: 하네스, RAG 시범, 백엔드

### 회사에서 해 본 LLM과 에이전트

**1. 회사에서 LLM이나 AI 에이전트를 직접 다뤄 본 경험이 있나요?**

> 있습니다. 클라이언트개발팀 기술 리드로서 팀 생산성을 올리려고 2026년 1월부터 팀 AI 에이전트 하네스를 설계, 구축, 운영하고 있습니다. Jira 일감 하나로 에이전트가 요구사항 분석부터 테스트, 구현, 실기기 검증, PR, 완료 보고까지 하고 사람은 지시와 검수를 맡는 구조이고, AI를 쓰지 않던 팀원까지 지금은 모두 이 환경에서 개발합니다. 이와 별도로 사내 장비에서 RAG를 시범 구축했습니다.

- 메모: 통화 21:25, 21:28, 21:31. 경민 조언대로 에이전트 이야기는 기술 리드로서 팀 생산성을 올린 하네스로 시작하고, 실무진에게 내세울 것도 이것이다. 경민 예시 「5090으로 에이전트와 RAG를 붙여 봤다가 결과가 나빠 폐기」는 기록에 없어 쓰지 않는다. RAG는 하네스와 연결한 적이 없다. 58문항 1번, 108문항 1번과 같은 줄기.

**2. 사내에서 직접 만들어 본 AI 서비스는 무엇인가요?**

> 사내 장비에서 외부 API 없이 도는 팀 문서 질의응답 RAG를 시범 구축했습니다. 생성, 임베딩, 리랭커 모델을 vLLM으로 서빙하고, PostgreSQL과 pgvector에 저장해 BM25와 벡터를 섞은 하이브리드 검색 뒤 리랭킹하게 했습니다. 구성 요소는 Open WebUI 위에 조립했고, 검색과 생성이 모두 도는 시범 단계까지 했습니다.

- 메모: 통화 20:37. 통화에서는 「만든 것이 없다」고 답했지만 이 시범을 답으로 쓴다. 「회사가 과제로 GPU를 줬다」, 「앱 등록 규정 챗봇을 만들었다」, 「결과가 나빠 폐기했다」는 경민 예시라 쓰지 않는다. 시범의 계기, 기간, 문서 수, 사용 인원은 본인 확인. 58문항 12번, 108문항 42~45번.

**3. 그 경험을 우대 사항의 온프레미스 AI 서비스 구축 경험으로 볼 수 있나요?**

> 모델 서빙부터 임베딩, 검색, 생성까지 외부 API 없이 사내 장비에서 이은 경험이라 온프레미스 구성 경험으로 말씀드립니다. 망분리 환경이나 Kubernetes 위에서 서비스를 운영해 본 적은 없고, 시범에서 vLLM과 pgvector를 Docker 컨테이너로 띄워 구성한 데까지가 제 경험입니다.

- 메모: 통화 19:56, 19:57. 경민은 제주항공 서버 증설을 온프렘 경험으로 말하라고 했지만, 우대 사항은 AI 서비스 구축이고 증설을 맡은 기록도 없어 쓰지 않는다. 58문항 44, 45번.

### 모델, GPU, 파인튜닝

**4. 모델은 무엇을 썼나요? 왜 그 모델이었나요?**

> 생성 모델은 Qwen3-8B를 vLLM으로 서빙했고 생각 과정은 껐습니다. 임베딩은 bge-m3, 리랭커는 bge-reranker-v2-m3입니다. 셋 다 공개 가중치 모델이라 외부 API 없이 사내에서 서빙할 수 있고, 8B는 16비트 가중치가 약 16GB인 크기입니다.

- 메모: 통화 20:00, 20:39. 통화에서 말한 Qwen 28B, 29B와 「우리는 Gemma를 썼다」는 기록과 다르다. 면접에서는 Qwen3-8B로 답하고, Gemma가 다른 사내 서비스 이야기였는지는 본인 확인. 모델을 고른 이유와 생각 과정을 끈 이유도 본인 확인(58문항 15, 17번, 108문항 50번).

**5. GPU는 무엇을 썼나요? 8B, 26B 같은 숫자는 GPU 메모리와 어떤 관계인가요?**

> 사내 GPU 장비에서 돌렸습니다. 8B는 학습으로 정해진 가중치가 80억 개라는 뜻이고, 16비트로 올리면 가중치 하나에 2바이트라 약 16GB, 26B면 약 52GB가 듭니다. 여기에 동시 요청 수와 길이에 비례하는 KV 캐시가 더 필요하고, 한 번에 넣을 수 있는 입력 길이는 파라미터 수와 별개인 컨텍스트 길이로 정해집니다.

- 메모: 통화 20:00, 20:01, 20:03. GPU 모델과 대수는 기록에 없다. 통화에서 RTX 5090이라고 했지만 한 장과 두 장이 엇갈렸으니(원문 209~210행, 506, 520행) 본인 확인 뒤 말한다. 경민의 「파라미터 수가 곧 말뭉치, 입력 크기」라는 설명은 틀렸다. 58문항 51번.

**6. 파인튜닝도 해 봤나요?**

> 해 본 적 없습니다. 시범은 공개 모델을 추가 학습 없이 서빙하고, 사내 문서 지식은 RAG로 검색해 프롬프트에 넣었습니다. 자주 바뀌고 출처를 보여야 하는 문서 지식은 RAG가 맞고, 파인튜닝은 답변 형식이나 도메인 표현을 맞춰야 할 때 LoRA 같은 경량 방식으로 검토하는 순서로 봅니다.

- 메모: 통화 20:00, 20:02. 경민 예시 「Qwen 26B를 파인튜닝했다」, 「작은 데이터로 조그맣게 튜닝해 봤다」, 「Hugging Face의 튜닝된 모델을 썼다」는 기록에 없어 쓰지 않는다. 58문항 19번.

**7. 경량화나 양자화는 해 봤나요?**

> 양자화를 직접 적용해 비교해 본 경험은 없습니다. 양자화는 가중치를 더 적은 비트로 근사해 메모리를 줄이는 방법이고, 8비트는 손실이 작지만 4비트 이하로 갈수록 품질 손실이 커집니다. 운영이라면 GPU 메모리보다 가중치가 큰 모델을 올려야 할 때 양자화 모델을 원본과 같은 평가셋으로 비교해 쓸지 정합니다.

- 메모: 통화 20:03, 20:39. 양자화 적용은 기록에 없으니 시범에서 양자화된 가중치를 받아 썼는지 본인 확인. 확인 전에는 「적용하지 않았다」고 단정하지 않는다. 경민 예시 「Gemma 26B를 INT4, INT8로 양자화했다」는 쓰지 않는다. FP32, FP8의 숫자는 소수점 자릿수가 아니라 수 하나를 저장하는 비트 수다.

### 지식 적재, 저장소, 리랭킹

**8. 사내 문서, 곧 지식은 어떻게 넣었나요?**

> 팀 문서를 docling-serve로 텍스트로 바꾸고, Open WebUI 내장 분할기로 제목 기준 청크를 나눈 뒤 bge-m3로 임베딩해 pgvector에 넣었습니다. 모델을 학습시킨 것이 아니라, 질문이 오면 관련 청크를 찾아 프롬프트에 넣어 답하게 하는 방식입니다.

- 메모: 통화 20:40. 경민 예시 「규정집을 처음엔 LLM에 직접 넣다가 문서가 많아져 RAG로 옮겼다」는 기록에 없어 쓰지 않는다. 「RAG를 학습시켰다」고 말하지 않고, 청킹부터 적재까지는 임베딩이 아니라 인덱싱이라고 부른다. 하네스의 LLM Wiki 검색과는 별개 작업이다(108문항 44번). 58문항 12, 14번.

**9. RAG DB는 무엇을 썼고, 왜 PostgreSQL이었나요?**

> PostgreSQL에 pgvector 확장을 붙여 썼고, 사내 장비에 Docker 컨테이너로 띄웠습니다. pgvector는 테이블에 벡터 열과 유사도 연산, 벡터 인덱스를 더해 주므로 청크 원문, 문서 ID, 메타데이터를 벡터와 같은 테이블에 두고 한 SQL로 필터와 유사도 검색을 함께 할 수 있습니다. Open WebUI 앱 데이터도 같은 DB에 두었습니다.

- 메모: 통화 20:41, 21:21. pgvector를 고른 실제 이유는 기록에 없어 본인 확인. 경민 예시 「회사에 널려 있는 PostgreSQL을 썼다」, 「무료 오픈소스라 유지보수 지원도 된다」는 기록과 다르거나 틀려 쓰지 않는다. 규모가 커지면 전용 벡터 DB를 검토한다는 꼬리는 58문항 37번.

**10. 그래프 DB, 예를 들어 Neo4j는 왜 안 썼나요?**

> 시범은 팀 문서에서 근거 청크를 찾아 답하는 질의응답이고, 벡터 검색과 키워드 검색을 섞은 하이브리드 검색으로 구성했습니다. 그래프 DB는 노드와 관계를 저장하고 따라가는 DB라, 쓰려면 문서에서 엔티티와 관계를 뽑아 그래프를 만드는 모델링이 먼저 필요합니다. GraphRAG에서 LLM 비용은 그래프 질의 자체가 아니라 이 추출 단계와 자연어 질문을 질의로 바꾸는 단계에서 듭니다. 여러 단계 관계를 따라가야 답이 나오는 질문이 많아지면 GraphRAG를 검토할 대상입니다.

- 메모: 통화 20:29, 20:32. 그래프 DB를 쓰지 않은 실제 이유는 본인 확인. 경민의 「Neo4j는 LLM이 있어야 하고 그래프를 타면 LLM 호출 비용이 든다」는 틀렸다. Cypher 질의 자체에는 LLM이 필요 없고, 비용은 그래프 구축과 자연어 질문을 질의로 바꿀 때 든다. pgvector는 그래프 DB를 대신하지 않는다.

**11. 리랭킹은 써 봤나요? 비용은 어떻게 보나요?**

> 구성해서 썼습니다. 하이브리드 검색으로 넓게 뽑은 후보를 bge-reranker-v2-m3가 질문과 함께 읽어 관련도 순으로 다시 매깁니다. 리랭커는 후보마다 추론을 한 번씩 하니 후보 수만큼 지연과 GPU 연산이 늘고, 외부 API라면 그만큼 호출 비용이 듭니다. 그래서 상위 후보에만 쓰고, 운영이라면 리랭커 없이도 평가셋 재현율이 목표를 넘을 때 끄는 것도 선택지입니다.

- 메모: 통화 20:09, 20:11, 20:13. 경민의 「개발할 때는 끄고 쓴다」, 「최후 수단으로 켠다」 틀은 리랭킹을 구성했다고 쓴 제출본과 어긋나 쓰지 않는다. 리랭킹은 생성 결과를 여러 번 다시 돌리는 것이 아니라 생성 전에 검색 후보 순서를 다시 매기는 단계다. 효과 수치는 본인 확인(108문항 47번). 58문항 13번.

### 하네스 에이전트와 본인 역할

**12. 하네스 위의 개발 에이전트와 백엔드에서 도는 에이전트는 같은 경험인가요?**

> 같은 경험은 아닙니다. 도구를 MCP 서버로 만들어 붙이고, 컨텍스트를 역할별로 나누고, 권한과 검증 게이트로 결과를 통제하는 부분은 겹칩니다. 다른 점은 도구 호출 루프와 대화 세션을 Claude Code가 돌린다는 것이고, 저는 그 위에 작업 단계별 상태 저장과 재개, 검증 장치를 만들었습니다. 서버에서 에이전트 루프를 돌리고 세션을 저장하며 API로 서빙하는 부분은 직접 구현해 본 적이 없습니다.

- 메모: 통화 19:40, 22:29. 경민의 「플랫폼에서 도는 에이전트와 적용 기술은 똑같다」는 틀렸다. 「전사에서 실행되는 에이전트를 만들었다」도 기록과 다르다. 하네스는 클라이언트개발팀 단위다. 단계별 상태 저장과 재개는 /Users/hwangbomin/career/career-ops/output/portfolio/포트폴리오-hanalife-ai-service.md 46행 기록이라 「상태 관리는 Claude Code가 맡았다」고 줄여 말하지 않는다. 도구 호출 루프 직접 구현 여부는 108문항 40번, 루프 구조는 58문항 22번.

**13. 그럼 에이전트 개발에 LangGraph나 LangChain을 써 봤나요?**

### 파라미터, 컨텍스트, 토큰

**22. 그럼 한 번에 넣을 수 있는 입력 길이는 무엇으로 정해지나요?**

**23. 토큰은 단어와 같은 건가요? 토크나이저는 무엇을 하나요?**

> 같지 않습니다. 토크나이저가 문장을 어휘 사전에 있는 조각으로 잘라 번호로 바꾸고, 그 조각 하나가 토큰입니다. 지금은 BPE 같은 서브워드 방식이라 자주 쓰는 말은 한 토큰, 드문 말은 여러 조각이 되고, 단어나 형태소 경계와 맞지 않을 때가 많습니다. 한국어는 토크나이저에 따라 같은 내용도 영어보다 토큰이 많이 나와서 비용과 컨텍스트 계산에 반영해야 합니다.

**24. 예전 Bag of Words와 지금 LLM은 텍스트를 다루는 방식이 어떻게 다른가요?**

> Bag of Words는 단어 순서를 버리고 문장을 단어별 출현 횟수로 나타내서, 같은 단어로 순서만 바꾼 문장은 같은 벡터가 됩니다. 지금 LLM은 토큰을 임베딩 벡터로 바꾸고 위치 정보를 더한 뒤, 트랜스포머의 어텐션이 앞선 토큰들과의 관계를 계산해 같은 단어도 문맥에 따라 다른 표현이 됩니다. 추론할 때는 순전파로 다음 토큰의 확률을 내고, 학습할 때는 순전파로 낸 예측과 정답의 오차를 역전파로 거슬러 보내 가중치를 고칩니다.

- 메모: 통화 19:42. 동료에게 들은 포워드, 백워드는 순전파와 역전파이고, 선형대수는 이 계산에 쓰는 수학 도구다. GPT 계열 LLM은 앞선 토큰만 보는 인과 어텐션이라 「앞뒤 문맥」이라고 하지 않는다. 앞뒤를 함께 보는 것은 BERT 같은 인코더 모델이다.

**27. 온프레미스에서 모델을 고를 때 기준은 무엇인가요? 큰 모델일수록 좋은 건가요?**

> 우리 업무 질문으로 만든 평가셋에서 필요한 정답률을 넘는 모델 가운데, 가진 GPU에 올라가고 목표 응답 시간을 지키는 가장 작은 모델을 고릅니다. 그다음 한국어 성능, 컨텍스트 길이, 도구 호출과 구조화 출력 지원, 라이선스를 봅니다. 같은 세대면 큰 모델이 대체로 낫지만 세대가 바뀌면 작은 최신 모델이 큰 이전 모델보다 나은 경우가 많아, 크기만으로 정하지 않습니다.

- 메모: 통화 19:59. 경민이 면접에서는 정확도 대신 그냥 성능이라고 말하라며 30B보다 100B가 좋다는 식으로 크기 순서를 외워 둔다고 한 말은 같은 세대 안에서만 맞다. 시범에서 Qwen3-8B를 고른 이유는 본인 확인(108문항 50번). 58문항 17번 꼬리의 「8B로 충분한가」와 맞춘다.

### 서빙 엔진과 GPU 메모리

**28. 서빙 엔진은 무엇을 하나요? Ollama와 vLLM은 무엇이 다른가요?**

> 서빙 엔진은 모델 가중치를 GPU에 올리고, 요청을 받아 토큰을 생성해 API로 돌려줍니다. Ollama와 vLLM은 같은 것을 로컬과 서버에서 다르게 부르는 이름이 아니라 서로 다른 엔진입니다. Ollama는 개인 PC에서 양자화된 모델을 쉽게 받아 돌리는 데 맞춰져 있고, vLLM은 GPU 서버에서 여러 요청을 연속 배치로 묶고 KV 캐시를 블록 단위로 관리해 처리량을 높입니다. 시범에서는 생성, 임베딩, 리랭커 세 모델을 모두 vLLM으로 서빙했습니다.

- 메모: 통화 20:22. 경민의 「로컬에서는 Ollama, 서버에서는 vLLM이라고 부른다」, 「모델 자체가 Ollama 같은 것」은 틀리다. 58문항 16번, 108문항 42번과 맞춘다.

**29. 그러면 모델 파일, 서빙 엔진, 애플리케이션은 각각 무엇을 맡나요?**

> 모델 파일에는 구조 설정, 토크나이저, 가중치가 들어 있고 그 자체로는 실행되지 않습니다. 서빙 엔진이 그 가중치를 GPU에 올려 추론을 돌리고 OpenAI 호환 API를 엽니다. 그 API를 부르는 쪽이 애플리케이션으로, 시범에서는 Open WebUI가 화면, 검색, 프롬프트 구성을 맡고 vLLM을 호출했습니다.

- 메모: 통화 20:22. 「가중치 아래에 애플리케이션 레이어가 있다」고 내가 들었다고 한 설명을 확인하던 대목이다. 모델 안에는 가중치 레이어만 있고, 가중치를 올려 요청과 잇는 것은 서빙 엔진이다.

**30. GPU 메모리는 어떻게 잡나요? 32GB GPU 한 장에 몇 B 모델까지 올라가나요?**

> 가중치는 파라미터 수에 파라미터당 바이트를 곱해 잡습니다. 16비트면 1B당 약 2GB라 8B는 약 16GB로 한 장에 올라가고, 20B대 후반은 약 56GB라 양자화 없이는 올라가지 않습니다. 여기에 동시 요청 수와 길이에 비례하는 KV 캐시와 엔진 여유분이 붙으니, 16비트 그대로라면 10B 남짓까지로 보고 정확한 상한은 최대 길이와 동시 요청 수를 정해 계산합니다. 4비트로 줄이면 1B당 0.5GB 남짓이라 20B대 모델도 가중치가 15GB 안팎으로 들어갑니다.

- 메모: 통화 20:00, 20:02. 시범 장비는 「사내 GPU 장비」로 말한다. 통화에서 RTX 5090이라고 했지만 한 장, 두 장이 엇갈렸으니 종류와 대수는 본인 확인(108문항 45번). 58문항 17번 꼬리, 51번과 맞춘다.

### 양자화

**31. 양자화는 무엇이고, FP16, FP8, INT8, INT4는 무엇이 다른가요?**

> 양자화는 가중치를 더 적은 비트로 근사해 저장하는 것입니다. 뒤의 숫자는 소수점 자릿수가 아니라 수 하나를 저장하는 비트 수라서, FP16에서 8비트로 가면 가중치 메모리가 절반, 4비트면 4분의 1이 됩니다. FP8과 INT8은 같은 8비트지만 부동소수점과 정수라는 표현 방식이 다르고, 8비트는 정확도 손실이 작은 편이며 4비트 이하로 갈수록 손실이 커집니다. 그래서 적용 전후를 같은 평가셋으로 비교해 정합니다.

- 메모: 통화 20:03. 경민의 「FP32와 FP8은 소수점 8자리, 32자리 차이」와 내가 한 말 「소수점을 잘라 정수로 만든다」는 둘 다 틀리다. 58문항 50번과 맞춘다.

**32. 양자화를 직접 적용해 본 적이 있나요?**

> 적용한 경험은 없습니다. 적용한다면 AWQ나 FP8처럼 vLLM이 지원하는 방식으로 양자화된 체크포인트를 올리고, 원래 정밀도 모델과 같은 평가셋으로 정답률, 첫 토큰 지연, 동시 처리 수를 비교해 손실이 허용 범위인지 보고 정합니다. 작은 모델일수록 양자화 손실이 더 드러나서, 큰 모델을 4비트로 줄일지 작은 모델을 16비트로 쓸지도 같은 방식으로 비교합니다.

- 메모: 통화 20:39, 20:40. 경민이 짜 준 「Gemma 26B를 INT4, INT8로 양자화해 올렸다」는 기록에 없으니 말하지 않는다. 시범 Qwen3-8B를 어떤 정밀도로 서빙했는지는 기록에 없어 본인 확인. 통화 20:00에 모델을 Qwen 28B나 29B로 기억했는데 기록은 Qwen3-8B다. 20B대 후반이면 32GB 한 장에 양자화 없이 올라가지 않아 이 답과 부딪히니, 모델 크기를 본인 확인.

### 파인튜닝이 바꾸는 것

**33. 파인튜닝을 하면 무엇이 바뀌나요?**

> 모델의 가중치가 바뀝니다. 기존 가중치를 추가 학습으로 갱신하거나 LoRA처럼 덧붙인 작은 가중치를 학습해서, 같은 질문에도 답의 형식, 말투, 특정 작업 성능이 달라집니다. 하네스나 애플리케이션이 아니라 모델이 바뀌는 것이고, 레이어나 가중치를 덜어 내 모델을 줄이는 것은 가지치기라는 다른 기법입니다.

- 메모: 통화 20:22. 경민이 언급한 「레이어를 빼는 식」은 파인튜닝이 아니라 가지치기다.

**34. 회사에서 파인튜닝을 해 봤나요?**

> 해 보지 않았습니다. 시범에서는 공개 모델 Qwen3-8B를 튜닝 없이 vLLM으로 서빙했고, 팀 문서는 모델에 학습시키지 않고 RAG로 검색해 프롬프트에 넣었습니다.

- 메모: 통화 20:00, 20:02. 경민이 제안한 「Qwen 26B를 파인튜닝했다」, 「작은 데이터로 조그맣게 튜닝해 봤다」는 기록에 없으니 말하지 않는다.

**35. 파인튜닝은 왜 추론보다 메모리가 많이 드나요? LoRA와 QLoRA는 무엇을 줄이나요?**

> 학습에는 가중치 외에 기울기, 옵티마이저 상태, 역전파용 활성값이 함께 올라가서, 전체 파인튜닝은 추론보다 몇 배 메모리가 듭니다. LoRA는 원래 가중치를 고정하고 작은 저차원 어댑터 행렬만 학습해, 학습할 파라미터와 옵티마이저 상태가 보통 전체의 1% 이하로 줄어듭니다. QLoRA는 고정한 원래 가중치를 4비트로 양자화해 올리고 그 위에서 LoRA 어댑터를 학습해 가중치 메모리까지 줄입니다.

- 메모: 통화 20:02. 경민의 「실행 메모리 외에 데이터를 올릴 메모리가 필요하다」는 틀리다. 늘어나는 것은 데이터가 아니라 기울기, 옵티마이저 상태, 활성값이다. 58문항 19번 꼬리의 LoRA 답과 맞춘다.

### 파인튜닝과 RAG 선택

**36. 약관이나 사내 규정처럼 자주 바뀌는 지식을 답하게 하려면 파인튜닝과 RAG 중 무엇을 쓰나요?**

> RAG입니다. 파인튜닝으로 넣은 지식은 규정이 바뀔 때마다 다시 학습해야 하고, 답의 출처를 대기 어렵고, 지운 내용을 모델에서 빼기도 어렵습니다. RAG는 바뀐 문서만 다시 색인하면 바로 반영되고 근거 문서를 함께 보여 줄 수 있으며, 시행일을 메타데이터로 두면 질문 시점에 맞는 판을 찾게 할 수 있습니다. 파인튜닝은 답변 형식이나 도메인 표현처럼 잘 바뀌지 않는 것을 맞출 때 씁니다.

- 메모: 통화 20:06, 20:21. 「12월 3일의 의미가 해마다 바뀌는데 그때마다 튜닝할 것이냐」는 예가 나왔다. 58문항 19번과 맞춘다. 경민의 「RAG는 정확도가 떨어져 요즘 안 쓴다」는 옮기지 않는다.

**37. 튜닝하지 않은 모델이 회사 데이터를 쓰게 하는 방법은 어떤 것이 있나요?**

> 모델은 그대로 두고 입력을 바꿉니다. 문서가 적으면 컨텍스트에 통째로 넣고, 많으면 RAG로 관련 청크만 검색해 프롬프트에 넣고, 파일 목록이나 색인을 주고 에이전트가 도구로 찾아 읽게 할 수도 있습니다. RAG는 모델을 학습시키는 것이 아니라 조회하는 것이고, 지식을 가중치에 넣는 방법이 파인튜닝입니다. 하네스에서는 제가 Python으로 직접 만든 지식베이스 검색 MCP 서버로 에이전트가 필요한 문서를 도구로 찾아 읽게 했고, 이것은 RAG 시범과 별개입니다.

- 메모: 통화 20:19, 20:53. 「RAG를 학습시켰다」고 말하면 틀린다. 하네스의 지식베이스 검색은 RAG 시범과 연결한 것이 아니다(108문항 44번).

### 학습 데이터와 평가 방식

**38. 지도 파인튜닝 데이터는 어떤 형태로 만드나요?**

> 질문이나 지시와 그에 대한 모범 답변을 짝지은 데이터입니다. 대화형 모델이면 시스템, 사용자, 어시스턴트 메시지를 모델의 채팅 템플릿에 맞춰 넣고, 보통 답변 부분에만 손실을 계산합니다. 문서의 단어를 가리고 맞히게 하는 방식은 BERT 같은 마스크 언어 모델의 사전학습이라 다른 것입니다. 금융 데이터라면 모델이 학습 데이터를 그대로 내보낼 수 있어 학습 전에 개인정보를 지웁니다.

- 메모: 통화 20:20. 경민의 「주요 단어를 형광펜으로 지우고 학습지를 풀게 한다」 비유는 마스크 언어 모델 사전학습 설명이라 지도 파인튜닝 답으로 쓰지 않는다. 58문항 19번 꼬리의 개인정보 위험과 맞춘다.

**39. 큰 모델이 작은 모델을 가르치는 것과 큰 모델이 답을 채점하는 것은 같은 방식인가요?**

> 다릅니다. 지식 증류는 작은 학생 모델이 큰 교사 모델의 출력이나 확률 분포를 따라 배우게 해서, 큰 모델의 능력을 작은 모델로 옮기는 학습 방법입니다. LLM-as-a-judge는 LLM이 답을 채점하는 평가 방법이고, 그 점수를 보상으로 학습하면 AI 피드백 강화학습이 됩니다. 하네스의 코드 리뷰에서는 기계로 판정할 수 있는 축은 스크립트로 검사하고, 판단이 필요한 축을 LLM이 보게 나눴습니다.

- 메모: 통화 20:20. 경민이 말한 「티처 스튜던트 방식」은 비싼 모델이 채점만 하는 것이라 표준 의미의 지식 증류가 아니라 LLM-as-a-judge에 가깝다. 리뷰 축 구성(스크립트 3개, LLM 11개, 별도 검사 위임 2개)은 108문항 20번, 22번과 맞춘다.

**40. 강화학습에서 보상은 무엇이고 어떻게 정하나요?**

> 보상은 모델의 답이 얼마나 좋은지 매긴 점수이고, 강화학습은 보상이 높은 답을 더 내도록 가중치를 고칩니다. 사람이 두 답 중 나은 쪽을 고른 선호 데이터로 보상 모델을 학습해 쓰면 RLHF, 그 판단을 AI가 하면 RLAIF입니다. 수학 정답이나 코드 테스트 통과처럼 맞고 틀림을 기계로 확인할 수 있으면 그 결과를 바로 보상으로 씁니다.

- 메모: 통화 20:20. 경민이 이름을 기억하지 못한 「사람이 직접 채점하는 방식」은 RLHF를 가리킨 것으로 보인다. 선호 데이터로 보상 모델 없이 바로 학습하는 DPO도 꼬리로 나올 수 있다.

## 3. RAG, 임베딩, 검색, 벡터 DB와 그래프 DB

### RAG의 단계와 구성

**41. RAG를 단계로 나눠 설명해 주세요.**

> RAG는 검색 증강 생성이고 검색, 증강, 생성의 세 단계입니다. 질문과 관련된 문서를 찾고, 찾은 문서를 프롬프트에 넣고, LLM이 그 근거로 답을 만듭니다. 요청 하나는 질문 임베딩, 검색, 리랭킹, 프롬프트 구성, 답변 생성 순서로 흐르고, 제가 시범 구축한 구성은 이 검색 단계를 BM25와 벡터를 섞은 하이브리드 검색으로 했습니다.

- 메모: 통화 19:41, 20:07, 20:09. RAG의 G는 생성이다. 경민의 「Retrieval Augmented Graph」 풀이와 「RAG는 말뭉치 저장소」 설명은 틀림. 58문항 12번, 108문항 42번과 같은 구성.

**42. 회사 문서를 RAG에 넣으면 모델이 그 내용을 학습하는 건가요?**

> 아닙니다. RAG는 질문할 때마다 문서를 조회해 프롬프트에 넣는 방식이라 모델 가중치는 바뀌지 않습니다. 그래서 문서를 고치면 다음 질문부터 바로 반영되고, 답에 근거 문서를 붙일 수 있습니다. 지식을 가중치에 넣는 것은 파인튜닝이고, 자주 바뀌는 사내 규정은 파인튜닝보다 RAG가 맞습니다.

### 생성형 LLM 호출을 줄이는 검색 설계

**54. LLM 호출 비용과 응답 지연을 생각하면 질의응답 흐름을 어떻게 짜나요?**

> 생성형 LLM 호출을 마지막 단계에 둡니다. 앞에서 키워드 검색, 메타데이터 필터, 벡터 검색, 리랭킹으로 근거를 좁히고, LLM은 그 근거로 답을 쓰는 데 씁니다. 검색은 수십 밀리초 단위로 끝나지만 생성은 수 초가 걸리고, 자체 서빙이면 GPU를, API면 호출 비용을 쓰기 때문입니다. 규칙으로 풀기 어려운 의도 해석이나 여러 근거를 묶는 설명에는 LLM을 넣고, 그 경계는 단계마다 지연과 정답률을 재서 정합니다.

- 메모: 통화 21:14, 21:17, 21:18, 21:19. 임베딩 검색과 리랭킹도 모델 추론이라 「AI 없이」가 아니라 「생성형 LLM 호출 없이」라고 말한다. 58문항 50번.

### 벡터 DB와 그래프 DB

**58. 벡터 검색으로 안 풀리는 질문은 GraphRAG로 푸나요?**

- 메모: 통화 20:28. 「RAG가 잘못 쌓이면 고치기 어려워서 GraphRAG가 나왔다」는 정리는 틀림.

**59. 그래프 DB를 써 봤나요? 온톨로지와는 어떤 관계인가요?**

- 메모: 통화 20:29, 20:32, 20:34. 그래프 DB 사용 기록은 없고 통화에서 잘 모른다고 답한 것이 근거라 본인 확인. 경민의 「그래프를 타는 순간 LLM 비용이 든다」, 「온톨로지는 그래프를 검색하는 방법」은 틀림. LLM 비용은 그래프를 만들 때와 자연어 질문을 질의로 바꿀 때 든다. 「pgvector가 그래프 DB를 대신한다」고 말하지 않는다.

**60. 지금은 PostgreSQL에 쌓아 두고 나중에 그래프 DB로 옮기면 되지 않나요?**

> 옮겨 넣기만 해서는 그래프가 되지 않습니다. 무엇을 노드로, 무엇을 관계로 둘지, 관계에 어떤 속성을 붙일지 정하는 모델링이 먼저입니다. 테이블의 행은 노드로, 외래 키와 조인 테이블은 관계로 옮기는 식으로 설계하고, 문서 본문 속 관계는 엔티티와 관계를 추출하는 단계가 따로 필요합니다.

### 챗 에이전트와 도구 호출의 주체

**61. 챗봇과 에이전트는 무엇이 다른가요?**

**63. 그 반복 구조를 ReAct라고 부르던데, ReAct는 무엇인가요?**

> ReAct는 추론과 행동을 번갈아 하는 에이전트 패턴입니다. 모델이 지금 무엇이 필요한지 판단하고, 부를 도구를 정하고, 실행 결과를 관찰한 뒤 다시 판단하는 과정을 답이 나올 때까지 되풀이합니다. 지금 도구 호출 API로 돌리는 에이전트 루프도 기본 구조가 같습니다. 재시도 기법이 아니고, 검색 결과 순서를 다시 매기는 리랭킹과도 다른 개념입니다.

### MCP와 사내 API 연결

**64. MCP 서버에 있는 도구 목록은 LLM에게 어떻게 전달되나요?**

> MCP 클라이언트가 서버에 연결해 tools/list 요청을 보내면, 서버가 도구마다 이름, 설명, 입력 JSON Schema를 돌려줍니다. 에이전트는 이 목록을 모델 요청에 도구 정의로 함께 넣고, 모델이 도구를 고르면 클라이언트가 tools/call 요청으로 서버에 실행을 맡깁니다. 모델은 설명을 읽고 도구를 고르기 때문에, 언제 쓰고 언제 쓰지 말지와 입력 제약을 설명에 어떻게 적느냐가 곧 프롬프트 설계입니다. 제가 Python으로 만든 SonarQube 조회와 지식베이스 검색 MCP 서버도 이 규격대로 도구를 내놓습니다.

- 메모: 통화 20:42. 경민이 예로 든 「tools.json」 같은 표준 파일은 없다. 통화에서는 「AI가 만들어 준다」고 약하게 말했지만 기록상 SonarQube 조회와 지식베이스 검색 MCP 서버는 직접 만들었다. 본인 확인: MCP 클라이언트를 따로 만든 적이 있는지. 58문항 8번과 맞춘다.

**65. API를 바로 부르면 되는데, MCP는 왜 나왔나요?**

**66. 그러면 에이전트가 사내 업무시스템 API를 호출하게 하려면 무엇을 준비해야 하나요?**

**67. MCP 말고 A2A라는 말도 나오던데, 둘은 어떻게 다른가요?**

### 사람 개입, 상태 저장, 멈출 조건

**72. 에이전트가 일을 하다가 필요한 값이 빠져 있으면 어떻게 처리하나요?**

### 에이전트 프레임워크

**75. LangChain과 LangGraph는 어떻게 다른가요?**

> 둘 다 LangChain Inc.가 만든 오픈소스이고, LangGraph가 LangChain의 새 이름은 아닙니다. LangChain은 모델 연동, 프롬프트 템플릿, 검색기, 도구 연결 같은 부품과 그것을 한 방향으로 잇는 체인을 줍니다. LangGraph는 상태, 노드, 간선으로 흐름을 그래프로 짜는 라이브러리라 분기와 되돌아가기, 재시도를 표현할 수 있고, 체크포인터와 interrupt로 상태 저장과 사람 개입을 지원합니다. 그래서 대신하는 관계가 아니라 함께 씁니다.

- 메모: 통화 20:48, 20:55. 경민은 「같은 재단」, 「옛날 것이 LangChain, 요즘 것이 LangGraph」, 「재시도 때문에 이름을 LangGraph로 바꿨다」고 했으나 틀린 설명이다. 58문항 23번과 맞춘다.

**76. LangGraph가 그런 기능을 준다면, 하네스에서 직접 만든 것은 LangGraph의 무엇에 대응하나요?**

> LangGraph로 옮겨 본 적은 없고, 옮긴다면 워크플로의 단계는 노드, 단계 사이에 넘기는 작업 정보는 그래프 상태가 됩니다. 검증에서 반려되면 구현으로 되돌아가는 흐름은 조건 간선으로 두고, 회차 수와 반려 사유를 상태에 담아 상한에 닿으면 그 간선에서 끝내게 합니다. recursion limit은 그래도 끝나지 않을 때 오류로 끊는 안전장치로 둡니다. 단계별 상태 저장은 체크포인터가, 계획 승인 같은 사람 지점은 interrupt가 맡습니다.

- 메모: 통화 20:58. 상태 머신, 재시도, HITL이 LangGraph 안에 있다는 경민 설명에 맞춘 비교다. LangGraph로 옮겨 본 적은 없으니 설계 비교로만 말한다. 「써 봤냐」는 질문과 답은 1절 「하네스 에이전트와 본인 역할」 묶음에 있다. recursion limit이 정상 종료가 아니라 GraphRecursionError를 내는 상한이라는 점은 LangGraph 공식 문서로 확인했다.

**77. LangGraph로 RAG를 붙인 챗 에이전트를 만든다면 어디부터 보나요?**

> 만들어 본 적은 없어서 설계로 말씀드리면, 모델을 어떻게 연결하는지, 검색을 어느 노드에 붙이는지, 시스템 프롬프트와 사용자 입력을 각각 어디에 넣는지부터 봅니다. 흐름은 의도 분류 노드가 검색이 필요한 질문만 검색 노드로 보내고, 검색 노드는 임베딩 모델로 질의를 벡터로 바꿔 벡터 DB를 조회합니다. 생성 노드는 시스템 프롬프트의 지침, 검색 결과, 사용자 질문을 나눠 넣어 모델을 부릅니다. vLLM으로 서빙한 모델은 OpenAI 호환 API를 열어 주므로 그 연동 부품으로 붙입니다.

- 메모: 통화 20:57. 경민이 꼽은 키워드는 LLM 연결, RAG, 임베딩 검색, 시스템 프롬프트와 사용자 입력 위치다. 유사도 검색은 LLM이 아니라 임베딩 모델과 벡터 DB가 한다(통화 20:51 정정). 만들어 본 적은 없으니 설계로만 말하고, RAG 시범은 Open WebUI로 조립해 에이전트와 연결하지 않았다고 구분한다.

**78. Google ADK나 OpenAI Agents SDK는 써 봤나요?**

> 써 보지 않았습니다. ADK는 Google의 Agent Development Kit 제품 이름이고, OpenAI 쪽은 Agents SDK라는 이름입니다. 둘 다 LangGraph와 같은 층의 에이전트 프레임워크로, 에이전트와 도구를 정의하면 실행 루프를 대신 돌려 줍니다. 고를 때는 쓰려는 모델과 배포 환경을 먼저 보고, 온프레미스에서 공개 가중치 모델을 쓴다면 특정 회사 모델이나 클라우드에 묶이지 않는지를 봅니다.

- 메모: 통화 20:54, 20:59. 경민은 이런 도구를 묶어 「ADK」라 부르고 SDK와 구분한다고 했으나, ADK는 Google 제품 이름이고 LangGraph까지 묶을 때는 「에이전트 프레임워크」라고 한다.

### AI 서비스의 계층과 데이터 보호

**84. 화면에서 LLM 서버를 바로 부르면 안 되나요?**

> 안 됩니다. LLM과 검색 색인은 사내 문서와 데이터에 닿기 때문에, 외부에 직접 열면 권한 밖 문서가 답변으로 새고 무단 호출이나 프롬프트 인젝션을 막을 지점이 없습니다. 그래서 백엔드가 사내 SSO 토큰으로 사용자와 권한을 확인하고, 그 권한으로 검색 범위를 거른 뒤 모델을 부르고 호출 기록을 남깁니다. 화면에는 정해진 기능만 API로 열어 둡니다.

- 메모: 통화 21:03. 경민의 「튜닝한 모델은 데이터 뭉치를 들고 있다」는 파인튜닝한 경우의 학습 데이터 노출 위험이고, 파인튜닝 경험은 없으니 내 사례로 말하지 않는다. 권한 거르기는 검색 단계에서 한다(58문항 41번, 48번).

### 폐쇄망과 망분리에서 개발하는 방식

**86. 망분리 환경에서는 개발과 배포를 어떻게 하나요?**

> 망분리 환경에서 개발하거나 운영해 본 경험은 없어서 알고 있는 방식으로 답하면 이렇습니다. 회사마다 다르지만, 인터넷이 되는 개발 환경에서 개발하고 검증한 뒤 컨테이너 이미지나 패키지로 묶어 정해진 반입 절차로 업무망에 들여옵니다. 모델 가중치, Python 패키지, 이미지는 버전과 해시를 고정해 내부 저장소와 레지스트리에 두고, 업무망의 테스트 결과나 로그를 밖으로 가져갈 수 있는지는 회사 보안 기준을 따릅니다.

- 메모: 통화 21:04. 원스토어 개발망은 망분리 환경이 아니라 망분리 경험이라고 말하지 않는다. 58문항 44번과 맞춘다.

**87. 이미지로 묶어 반입할 때는 무엇을 챙기나요?**

> 이미지는 태그와 다이제스트로 버전을 고정하고, docker save로 묶어 반입한 뒤 docker load나 내부 레지스트리로 씁니다. 모델 가중치는 이미지에 넣지 않고 볼륨으로 붙여 모델만 따로 교체할 수 있게 하고, 반입 전에 취약점 점검과 라이선스 확인을 거칩니다. 제 경험은 시범에서 vLLM과 pgvector를 Docker 컨테이너로 띄운 데까지이고, 반입 절차나 Kubernetes 운영은 해 보지 않았습니다.

- 메모: 통화 21:05. 사외망에서 개발해 이미지나 바이너리로 묶어 넣는다는 것은 경민의 실무 사례라 내 경험으로 말하지 않는다. 58문항 45번과 맞춘다.

### 금융권의 점진적 도입과 LLM 호출

**88. 금융권은 왜 생성형 AI를 바로 전면에 넣지 않고 룰 기반과 검색부터 쌓는다고 보나요?**

> 결과를 설명하고 책임져야 하는 업무가 많기 때문이라고 봅니다. 규칙과 검색은 같은 질문에 같은 답을 내고 근거를 보여 줄 수 있지만, LLM은 확률로 답해 틀릴 수 있고 토큰과 GPU 비용, 응답 지연이 붙습니다. 망분리 규제로 외부 모델을 쓸 수 있는 범위도 아직 제한적입니다. 그래서 규칙, 키워드 검색, 하이브리드 검색으로 풀리는 것은 생성형 LLM 호출 없이 먼저 풀고, 그 과정에서 문서 색인과 메타데이터를 정리해 두면 나중에 LLM을 붙일 때 검색 품질이 받쳐 줍니다.

- 메모: 통화 21:07, 21:19, 21:21. 룰 기반은 규칙, 사전, 정규식으로 처리하는 방식 전반이라 키워드 검색과 같은 말이 아니고 하네스와도 다르다(경민 설명 틀림). 벡터 검색에도 임베딩 모델 추론은 필요하니 「AI 없이」라고 하지 않는다. 은행 사례와 응답 초 수치는 경민에게 들은 말이라 사실로 말하지 않는다. 하이브리드 검색 세부는 58문항 13번, 108문항 46번, 48번.

**89. 그럼 LLM은 어디에 쓰나요? 계속 덜 쓰면 AI 서비스라고 할 수 있나요?**

> 안 써도 되는 곳에는 덜 쓰는 것이 맞지만, 아예 안 쓰는 것은 답이 아니라고 봅니다. 답이 하나인 계산과 조회는 코드와 규칙으로 두고, 문서를 이해해 요약하거나 분류하는 일과 질문 의도를 해석하는 자리에는 LLM을 넣습니다. 당장 호출을 줄이더라도 검색 결과를 받아 답을 만드는 단계는 인터페이스로 남겨 두면, 모델이 좋아졌을 때 그 자리에 바꿔 끼우면 됩니다.

- 메모: 통화 21:18, 21:19. 「AI가 들어갈 자리는 남긴다」는 통화에서 나온 틀이다. 58문항 21번, 55번과 맞춘다.

### 상용 모델, 온프레미스 모델, 솔루션

**90. 상용 API와 사내 온프레미스 모델은 어떤 기준으로 고르나요?**

> 어떤 데이터가 모델에 들어가는지가 첫 기준입니다. 개인정보나 신용정보가 그대로 들어가는 작업은 공개 가중치 모델을 사내에서 서빙하는 쪽이 맞고, 가명 처리했거나 민감하지 않은 작업은 사내 기준이 허용하는 범위에서 상용 API를 검토합니다. 온프레미스는 GPU 비용과 서빙, 모델 교체 부담을 지고, 상용 API는 토큰 비용과 외부 의존을 집니다.

- 메모: 통화 20:18, 21:22. 온프레미스에서는 공개 가중치 모델을 vLLM 같은 서빙 엔진으로 그대로 쓰는 경우가 많고 파인튜닝은 필수가 아니다. 금융 규제와 샌드박스 세부는 58문항 46번과 맞춘다.

**91. 상용 모델을 쓰면 API 문서만 넣어 줘도 알아서 하지 않나요?**

> 그렇지 않습니다. 모델이 좋아도 사내 데이터는 모르기 때문에 문서 검색 색인, 호출할 API의 정의와 입력 스키마, 사용자 권한 통제는 그대로 만들어야 합니다. 상용 모델로 줄어드는 것은 모델 서빙과 튜닝 부담입니다. 하네스도 Claude를 썼지만 SonarQube 이슈와 지식베이스는 제가 MCP 서버로 만들어 붙여서 에이전트가 쓰게 했습니다.

**92. 그런 부분까지 갖춘 솔루션을 사면 되지 않나요? 솔루션 구매와 자체 개발은 어떻게 판단하나요?**

### 업계 동향과 에이전트 거버넌스

**93. AX라는 말을 많이 쓰는데, DT와는 무엇이 다르다고 보나요?**

> DT는 Digital Transformation, 곧 디지털 기술로 업무와 서비스 방식을 바꾸는 디지털 전환이고, AX는 AI Transformation, 곧 그 위에서 AI가 업무의 일부를 판단하고 처리하게 바꾸는 AI 전환입니다. DT로 쌓은 데이터와 시스템은 AX의 바탕이 되지만, AX는 결과를 누가 검수하고 책임지는지까지 업무 절차를 바꿔야 해서 DT를 빨리 끝낸 회사가 AX도 빠르다고 보지는 않습니다.

**94. AX가 화두가 된 지는 얼마나 됐다고 보나요? 생성형 AI가 대중화된 시점은 언제인가요?**

> 생성형 AI 대중화는 2022년 11월 ChatGPT 공개를 기점으로 약 4년으로 보고, AX는 그 뒤 기업들이 생성형 AI를 업무에 넣기 시작하면서 화두가 됐다고 봅니다. AI 연구는 수십 년 됐지만 일반 사용자와 기업이 생성형 AI를 쓰기 시작한 건 그때부터입니다. 그 사이 질의응답에서 RAG, 도구를 쓰는 에이전트로 쓰임새가 넓어졌고, 저도 올해 1월부터 팀 개발 업무를 에이전트 하네스로 옮겼습니다.

**96. 사내에 에이전트가 많아지면 무엇을 관리해야 한다고 보나요?**

> 에이전트를 만들기 쉬워진 만큼 사실과 다른 답을 내거나 잘못된 데이터를 쓰는 에이전트가 섞이기 쉽고, 같은 일을 하는 에이전트도 겹치기 쉽습니다. 그래서 등록 전에 평가 기준으로 검증하고, 에이전트마다 쓸 수 있는 데이터와 도구 권한을 정하고, 배포 뒤에는 사용 기록으로 계속 점검하는 체계가 필요하다고 봅니다.
