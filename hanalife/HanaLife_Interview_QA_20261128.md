### 기획부터 운영까지

### 생성형 AI와 환경

**15. 온프레미스나 망분리 환경에서 AI 서비스를 구축해 본 적이 있나요?**

### 하네스가 무엇인지

### 구조와 검증

**19. 에이전트를 역할별로 나눈 이유는 무엇인가요?**

> 컨텍스트와 권한을 나누기 위해서입니다. 한 에이전트가 기획부터 리뷰까지 다 하면 컨텍스트가 길어져 앞의 지시를 놓치고, 자기 코드를 자기가 리뷰하게 됩니다. 그래서 기획, 설계, 구현, 테스트, 보안, 리뷰 같은 역할로 나누고 역할마다 쓸 수 있는 도구를 제한했고, 검증 에이전트는 작업자와 분리된 읽기 전용으로 두었습니다.

- 근거: 이력서 「에이전트 설계(32종)」, AI 기술 표 「컨텍스트 엔지니어링」.

**20. 에이전트가 만든 결과를 어떻게 믿을 수 있나요?**

> 믿지 않고 검사하는 구조로 만들었습니다. 단계마다 통과 기준을 두고 못 넘으면 그 단계를 다시 하게 했고, 완료는 판정 스크립트로 화면, 로그, 서버 응답을 확인한 결과로만 인정합니다. 회차 중에 검사 기준 파일이 바뀌면 통과해도 무효로 처리해서 에이전트가 기준을 고쳐 통과하는 것을 막았고, 같은 반려 사유가 세 번 이어지면 멈추고 사람에게 넘깁니다.

- 근거: 이력서 「개발 루프」.
- 메모: 이 답은 금융 AI 서비스의 답변 검증 질문으로 이어지기 좋다. 「서비스에서도 생성 결과를 검증 단계로 거른다」로 연결한다.

**21. 훅으로는 무엇을 막았나요?**

> 파괴적 명령, 보호 브랜치 push, 외부 전송, Gradle 직접 실행, 무인 실행 중 질문을 막았습니다. 에이전트별로 쓸 수 있는 도구를 제한했고, 외부에서 읽어 온 내용은 지시가 아니라 데이터로 취급하게 규칙을 넣었습니다. push 전에는 코드 리뷰, 커밋과 PR 규약, 아키텍처 판정 검사를 훅으로 강제했습니다.

- 근거: 이력서 「통제, 검증」.

**22. MCP 서버는 무엇을 직접 만들었나요?**

> 기존 서버와 로컬 스크립트를 에이전트가 도구로 쓰게 MCP로 감쌌습니다. SonarQube 이슈 조회, 팀 지식베이스 검색, 제품별 빌드와 빌드 오류 보고 도구를 만들었고, 에이전트가 Gradle을 직접 못 부르게 훅으로 막아 빌드를 그 도구로 모았습니다. 팀원 하네스가 스킬과 훅 사용 기록을 숫자와 자산 이름만 동의를 받아 보내는 원격 수집 서버도 만들었습니다.

### 팀에 정착시킨 방법

**24. AI를 쓰지 않던 팀원은 어떻게 쓰게 만들었나요?**

> 개인 선택에 맡기지 않고 팀 개발 환경 자체를 하네스로 바꿨습니다. 사용자 정보와 작업 앱 저장소만 넣으면 동기화 스킬이 설치와 갱신을 맡게 해서 설정 부담을 없앴고, 저장소마다 빠진 규칙과 검증 장치를 점검해 채우게 했습니다. 사내 위키에 에이전트 가이드 12편과 기초 가이드 2편을 써서 교육했고, 주간보고 자동화처럼 모두가 매주 하는 일도 자동화했습니다.

**25. QA 결함 본인 0건, 팀 절반 수준이라는 수치는 어떻게 쟀나요?**

**26. 하네스를 만들면서 실패했거나 바꾼 것은 무엇인가요?**

- 근거: 통화 21:24:57~21:25:25 본인 말(「기본으로 로드되는 룰이 너무 커져서 에이전트로 쪼개고」, 「스킬도 너무 커서 에이전트 쪽으로 밀어 넣고」), 이력서 「하네스 최적화, 자가 개선」.

**27. 하네스를 운영하는 비용, 토큰은 어떻게 관리했나요?**

- 한계: 절감한 비용 수치는 기록에 없다. 리뷰 단계 수(5개 또는 6개)는 본인 확인.

### RAG 시범 구축

**28. RAG를 시범 구축했다고 했는데 구성을 설명해 주세요.**

- 한계: 검색과 생성이 모두 도는 시범 단계까지다. 팀 운영으로 넓히지 않았다.

**29. 그중 본인이 직접 구현한 부분은 어디인가요?**

> 모델 서빙과 저장소를 띄우고, 변환, 청크, 임베딩, 하이브리드 검색, 리랭커를 고르고 연결해 한 흐름으로 돌게 만든 것이 제 몫입니다. vLLM과 pgvector는 Docker 컨테이너로 띄웠습니다. 검색 알고리즘이나 오케스트레이션 코드를 처음부터 짠 것은 아니고, Open WebUI의 하이브리드 검색과 내장 분할기를 설정해 썼습니다.

- 근거: cv.md 863행, 1612행.

**30. RAG는 하네스와 어떻게 연결되어 있나요?**

> 연결되어 있지 않습니다. 이력서에는 하네스 항목 안에 같이 적었지만, RAG는 그와 별도로 팀 문서 검색을 시험한 일입니다. 하네스의 지식 검색은 RAG가 아니라 Markdown 산출물 지식베이스를 검색하는 스크립트 기반 MCP 도구로 했습니다.

**31. 왜 시범에서 멈췄나요?**

> 팀 전체로 넓히려면 장비와 문서 입력이 따라와야 했고, 그 두 가지가 시범 범위 밖이었습니다. 기술적으로는 지금 구성을 더 좋은 장비에 그대로 올리고 문서를 넣으면 넓힐 수 있다고 봤습니다.

**32. 답변 품질은 어떻게 평가했나요?**

> (본인 확인 뒤 채움.) 평가를 한다면 질문과 정답 근거 문서 쌍을 먼저 만들고, 검색은 정답 문서가 상위 몇 개 안에 들어오는지로, 생성은 답이 검색한 근거 안에서만 말했는지와 질문에 맞게 답했는지로 나눠 보겠습니다.

- 한계: 시범의 평가 방법, 문서 수, 사용 인원, 기간은 기록에 없다. 앞 문장은 직접 채우고, 뒤 문장은 「앞으로 한다면」으로 말한다.

**33. 생성 모델로 Qwen3-8B를 고른 이유는 무엇인가요?**

> (고른 이유를 본인 확인 뒤 채움.) 생각 과정을 출력하는 모드는 끄고 썼습니다. 금융 업무에 모델을 고른다면 사내 GPU 메모리에 올라가는 크기, 한국어 업무 문서에서의 답변 품질, 라이선스, 응답 지연을 기준으로 후보를 같은 질문 세트로 비교하겠습니다.

- 근거: cv.md 863행(「생각 과정 끔」).
- 한계: 고른 이유, 다른 모델과 비교했는지, 장비의 GPU 사양은 기록에 없다. 앞 괄호는 직접 채우고, 마지막 문장은 「한다면」으로 말한다.

**34. 리랭킹을 써 봤나요? 비용이 들지 않나요?**

> 시범에서 bge-reranker-v2-m3를 vLLM으로 띄워 하이브리드 검색 결과의 순위를 다시 매겼습니다. 리랭커는 생성 모델을 여러 번 돌리는 것이 아니라 질문과 문서 한 쌍씩 관련도를 매기는 작은 모델이라, 1차 검색으로 후보를 수십 개로 좁힌 뒤에만 돌리면 비용과 지연이 크지 않습니다. 검색이 처음부터 잘 맞으면 리랭커를 빼는 것도 방법이라, 평가 세트로 켰을 때와 껐을 때를 비교해 정합니다.

- 근거: cv.md 863행(리랭킹 bge-reranker-v2-m3 on vLLM).
- 메모: 통화 20:10~20:12 「리랭킹 써 봤나요, 그럼 어떻게 하냐」가 나온다고 했다. 경민의 「리랭킹은 100번씩 다시 돌리는 것」, 「저는 끄고 개발한다」는 설명과 예시는 쓰지 않는다. 리랭킹은 다시 생성하는 것이 아니다.

**35. 양자화나 경량화를 해 봤나요?**

> (본인 확인 뒤 채움.) 8B 모델은 16비트 그대로면 가중치만 약 16GB입니다. 다만 같은 GPU에 임베딩 모델과 리랭커까지 vLLM으로 띄우면 세 모델이 GPU 메모리를 나눠 쓰고 생성 모델의 KV 캐시에 남는 몫이 줄어서, 가중치만 보고 판단하지 않고 동시 요청 수와 문맥 길이까지 넣어 계산합니다. 메모리가 모자라면 8비트나 4비트로 양자화하고 업무 질문 세트로 품질 손실을 확인하겠습니다.

- 한계: 시범에서 양자화를 했는지는 기록에 없다. 「INT4나 INT8로 경량화했다」는 통화 20:40:16 경민 예시라 쓰지 않는다.
- 메모: 통화 20:03:02 「경량화 해 봤냐」가 나온다고 했다. vLLM은 기본으로 GPU 메모리의 90%를 미리 잡는다(gpu_memory_utilization 0.9). 한 GPU에 여러 모델을 띄우려면 인스턴스마다 이 값을 나눠 줘야 한다. 시범에서 세 모델을 같은 GPU에 띄웠는지는 본인 확인. 6절 「8B 모델을 올리려면 GPU 메모리가 얼마나 필요한가요?」 답과 같은 계산이다.

### 기술 리드와 리팩토링

**36. 서비스를 멈추지 않고 10년 넘은 앱의 구조를 어떻게 바꿨나요?**

> 한 번에 갈아엎지 않고 기능 개발과 함께 계층별로 옮겼습니다. 먼저 스티커스토어에 새 구조를 처음 적용한 뒤, 국내 앱은 Domain 계층을 먼저 분리했고 Data 계층은 그 과정에서 함께 정리했습니다. 이어서 Presentation, DataSource, UI 순으로 전체 계층을 옮기면서 MVC를 MVVM, MVI로 바꿨습니다. 그 과정에서 싱글턴 직접 참조를 Hilt 주입으로, 콜백 로더를 Flow로, 백그라운드 서비스를 WorkManager로 바꿔 핵심 다운로드, 설치, 자동 업데이트 경로의 백그라운드 서비스를 없앴습니다.

- 근거: 이력서 기술 리드 「기술 방향, 표준」, 리팩토링 「한 일」, 「결과」, cv.md 163행 「국내 앱 리팩토링 요약 3줄」(Domain, Data, Presentation, DataSource, UI 순), 사용자 정정 11-28(Domain을 먼저 분리, Data는 그 과정에서 함께 정리).
- 메모: 제출본은 「8년 넘은」이다. 11-25 사용자 결정으로 「10년 이상」을 쓰므로 면접에서는 「10년 넘게」로 말한다. 10년이 넘었으니 서류의 「8년 넘은」도 틀린 말은 아니다.
- 메모: AI 직무 면접이라 길게 끌지 않는다. 「돌아가는 시스템을 멈추지 않고 바꾼다」를 사내 업무시스템 연계로 잇는다(자기소개서 3번 강점 2).

**37. 팀원들이 새 구조에 반대하거나 따라오지 않으면 어떻게 했나요?**

> 새 구조를 샘플 아키텍처 프로젝트로 먼저 설명했습니다. 그 뒤 MVVM, MVI, Clean Architecture, 비동기와 DI, 테스트를 주제로 팀 세션을 반복했고, 구조와 개발 표준은 제안한 뒤 팀 합의로 확정했습니다. 리뷰 가이드를 팀 규칙에 넣어 리뷰에서 같은 기준으로 맞춰 가게 했습니다. QA팀이 검증 부담을 이유로 리팩토링에 반대했을 때는 리팩토링을 사업 과제와 묶어 함께 검증하기로 합의했습니다.

- 근거: 이력서 기술 리드 「팀 학습 주도」, 「리뷰 문화, 품질」, QA팀 사례는 사용자 확인 11-28.
- 메모: 「구체적으로 누가, 무엇을」이 오면 7절 「협업하면서 의견이 부딪혔던 경험」의 두 사례(QA팀 검증 부담, 팀원이 제안한 BaseViewModel)로 답한다.

### 서버 개발

**38. AK아이에스에서 제주항공 일을 할 때 서버 쪽은 어디까지 했나요?**

> AK아이에스 소속으로 고객사 제주항공의 일을 했습니다. 모바일 웹은 Spring 3.1 서버에서 JSP 화면 템플릿과 서버 처리를 고치고 jQuery와 Ajax로 화면 데이터를 처리했습니다. 사내 관리 웹페이지의 서버 API는 Spring Boot로 만들었고, 서비스 콘텐츠 관리 시스템은 AngularJS와 Spring Boot로 개발했습니다.

## 5. 통화에서 나온 질문: 실무 판단

### LLM을 어디에 쓸 것인가

**39. 공고에 LLM과 RAG를 붙이는 일이 있는데, 실무에서는 어떻게 하겠습니까?**

> LLM은 꼭 필요한 곳에만 쓰고, 그 앞을 싸고 빠른 단계로 채우겠습니다. 질문이 들어오면 키워드 검색과 메타데이터 필터, 벡터 검색으로 근거 문서를 먼저 찾고, 정해진 답이 있는 질문은 그 결과나 규칙으로 바로 답합니다. 문서를 읽고 정리해야 하는 질문에만 LLM을 마지막에 부르고, 나중에 모델이 좋아지면 그 자리만 바꿔 끼울 수 있게 단계를 나눠 두겠습니다.

- 메모: 통화 21:18~21:19 경민 논리 「LLM 안 써서 될 거면 덜 쓰는 게 베스트, 대신 AI가 들어갈 자리는 만들어 둔다, 맨 마지막에 넣는 게 저렴하다」. 비용(GPU 임대, 호출 비용)과 응답 시간이 이유다(21:14).
- 메모: 「왜 그렇게 생각해요?」 꼬리가 온다(21:19:57, 21:21:23). 이유는 비용, 응답 시간, 결과 예측 가능성 세 가지로 답한다.

**40. 에이전트는 확률로 움직이는데, 틀리면 책임은 어떻게 지나요? 차라리 규칙 기반이 낫지 않나요?**

### 왜 이 기술을 썼나

**41. 시범에서 왜 PostgreSQL과 pgvector를 썼나요?**

**42. 검색이 느리면 어떻게 하겠습니까?**

> 어디가 느린지부터 나눠 봅니다. 임베딩 추론, 벡터 검색, 리랭커, 생성 중 생성이 보통 가장 오래 걸리므로 답변은 스트리밍으로 먼저 보여 주고, 자주 묻는 질문은 결과를 캐시합니다. 벡터 검색 자체가 느리면 색인 설정을 조정하고, 키워드 검색은 Elasticsearch 같은 전용 검색 엔진으로 분리하는 것을 검토합니다.

- 메모: 통화 21:23:50 「Elasticsearch로 할 수 있으면 최대한, 느리면 Redis」. Redis는 캐시 용도로 말한다.

**43. 키워드 검색은 한국어에서 어떻게 하나요?**

> 한국어는 조사와 어미가 붙어 단어가 바뀌기 때문에, 형태소 분석기로 명사와 어간을 뽑아 색인하고 같은 방식으로 질문을 분석해 검색합니다. Elasticsearch라면 Nori 같은 한국어 분석기를 씁니다. 상품명과 특약명처럼 업무 고유어는 사용자 사전에 넣어야 쪼개지지 않습니다.

- 메모: 통화 21:11~21:13 형태소 분석 뒤 검색 엔진에 넣는 설명. 「한국어는 SVO」라는 말은 틀렸다(한국어 기본 어순은 SOV). 답에 쓰지 않는다.

**44. 벡터 검색만 쓰면 LLM 없이도 되지 않나요?**

> 생성 모델 호출 없이 비슷한 문서를 찾는 것은 됩니다. 다만 질문을 벡터로 바꾸는 임베딩 모델은 여전히 돌려야 합니다. 찾은 문서를 그대로 보여 주면 되는 경우는 검색만으로 끝내고, 여러 문서를 읽고 답을 정리해야 할 때만 생성 모델을 씁니다.

- 메모: 통화 21:13~21:14 경민 「그럼 AI 안 써도 돼요」는 생성 모델이 필요 없다는 뜻으로만 맞다.

**45. 문서를 그냥 LLM 컨텍스트에 다 넣으면 안 되나요? RAG는 왜 필요하나요?**

> 문서가 적으면 컨텍스트에 다 넣는 것이 더 간단하고 정확할 수 있습니다. 최신 규정 몇 개를 요약하는 정도라면 그렇게 합니다. 하지만 문서가 수천, 수만 건이면 컨텍스트에 다 들어가지 않고, 들어가더라도 길수록 비용과 지연이 커지고 중간 내용을 놓치기 쉬워서, 필요한 부분만 찾아 넣는 RAG가 필요합니다.

- 메모: 통화 20:15~20:17, 20:27~20:28 「자료 범위가 작으면 그냥 넣고, 10년치 문서는 RAG」. 「LLM 서치」, 「임베딩 서치」는 표준 용어가 아니니 쓰지 않는다. 20:40:34 「지식은 어떻게 하셨어요?」가 이 질문의 다른 형태다.

**46. 시스템 프롬프트와 사용자 입력은 어떻게 나눠 쓰나요?**

> 시스템 프롬프트에는 바뀌지 않는 것, 즉 역할, 답변 규칙, 금지 사항, 출력 형식을 둡니다. 사용자 입력에는 질문만 넣고, 검색한 문서는 따로 구분된 영역에 「참고 자료」로 넣어 모델이 그 안의 문장을 지시로 따를 가능성을 줄입니다. 이렇게 나눠 두는 것이 프롬프트 인젝션 위험을 줄이는 기본이고, 구분만으로 완전히 막을 수는 없어서 모델이 쓸 수 있는 도구와 권한도 최소로 둡니다.

- 메모: 통화 20:57:40 「LLM 어떻게 붙여, RAG 어떻게 붙여, 임베딩 검색 어떻게 해, 시스템 프롬프트는 어디다 쓰고 사용자 입력은 어디다 써」. 하네스의 「외부에서 읽은 내용은 지시가 아닌 데이터」와 연결한다.

**47. 그래프 DB는 써 봤나요? 왜 Neo4j를 안 쓰고 PostgreSQL을 썼나요?**

> 그래프 DB를 실무에서 써 본 적은 없습니다. 시범은 문서 질의응답이라 비슷한 문단을 찾는 벡터 검색과 키워드 검색으로 충분했고, 메타데이터와 앱 데이터까지 한 DB에서 다룰 수 있는 PostgreSQL이 운영하기 쉬웠습니다. 상품, 특약, 보장 조건처럼 관계를 여러 단계 따라가야 하는 질문이 많아지면 그때 지식 그래프를 검토하겠습니다.

- 한계: 그래프 DB 실무 경험 없음.
- 메모: 통화 20:29~20:33 「DB 뭘 쓸 거냐」, 「그래프 DB 써 봤냐」, 「왜 Neo4j 안 써」. 경민의 「그래프를 타는 순간 Neo4j 안에서 LLM 콜을 해서 돈이 든다」는 틀렸다. 그래프 조회 자체는 LLM 호출 없이 Cypher 질의로 된다. 비용은 문서에서 엔티티와 관계를 뽑아 그래프를 만들 때와 GraphRAG로 답을 만들 때 든다.

### 에이전트 상태와 지식 구조

**48. 에이전트가 대화나 작업 상태를 기억하게 하려면 무엇이 필요하나요?**

> 대화 이력과 작업 상태를 모델 밖에 저장해야 합니다. 대화 이력과 단계별 상태는 관계형 DB에 세션 단위로 남기고, 다음 요청 때 필요한 만큼만 불러 컨텍스트에 넣습니다. 하네스에서는 단계마다 상태를 저장해 진행이 끊겨도 그 단계부터 이어 가게 했고, 회차나 시간 상한에 걸리면 중간 저장 뒤 새 세션이 이어받게 했습니다.

- 근거: 포트폴리오 「단계마다 상태를 보고하고 저장해 진행이 끊겨도 그 단계부터 재개」, 이력서 「개발 루프」.
- 메모: 통화 21:34의 「그래프 DB가 검색, 캐시, 이력을 다 합친 저장소」라는 설명은 맞지 않는다. 그래프 DB는 관계 탐색용이다.

**49. 금융권에서 온톨로지나 지식 그래프는 왜 이야기되나요?**

> 상품, 특약, 보장, 고객 유형처럼 관계가 복잡한 지식을 엔티티와 관계로 정리해 두면, 「이 상품의 이 특약이 어떤 경우에 보장되나」 같은 여러 단계의 질문을 정확히 따라갈 수 있기 때문입니다. 벡터 검색은 비슷한 문장을 찾는 데 강하고 지식 그래프는 관계를 따라가는 데 강해서, 둘을 함께 쓰는 GraphRAG 방식이 이야기됩니다. 다만 관계형 데이터를 옮긴다고 그래프가 되는 것은 아니고, 무엇을 엔티티와 관계로 볼지 정하는 모델링이 먼저입니다.

- 메모: 통화 21:48 「임원들은 금융권 온톨로지나 지식 그래프, 임베딩에 관심」. 팀에서 온톨로지와 지식 그래프를 구축하고 있다는 기록(cv.md, 2026-10~ 진행 중)과 가이드 12편 주제가 온톨로지와 지식 그래프라는 기록이 있다. 「진행 중」, 「가이드로 정리」까지만 말한다.

**50. LangGraph나 LangChain을 써 봤나요? 에이전트는 무엇으로 개발했나요?**

> LangGraph와 LangChain은 실무에서 써 보지 않았습니다. 하네스는 Claude Code의 서브에이전트, 훅, 스킬 위에 설계했고, SonarQube 조회, 지식베이스 검색, 빌드 같은 도구는 스크립트 기반 MCP 도구로 만들어 붙였습니다. LangGraph는 에이전트의 단계를 상태 그래프로 정의하고, 상태를 체크포인트로 저장해 끊긴 지점부터 다시 시작하고, 사람 확인이 필요한 지점에서 멈추게 하는 프레임워크로 알고 있습니다. 하네스에서 단계별 상태 저장과 재개, 사람 승인 지점을 직접 설계한 것과 같은 개념이라 빠르게 옮겨 쓸 수 있습니다.

**51. 하네스 경험이 다른 모델이나 에이전트에도 통하나요?**

**54. 사내에 에이전트와 AI 서비스가 많아지면 무엇을 관리해야 하나요?**

## 6. 업무 지식: 공고의 LLM, RAG, 에이전트, 서빙

### RAG 설계

**55. 보험 약관과 상품 문서로 사내 질의응답 RAG를 만든다면 어떻게 설계하겠습니까?**

> 문서 수집과 변환, 청크 분할, 임베딩과 색인, 검색, 생성, 평가의 여섯 단계로 나누겠습니다. 약관은 장, 조, 항 구조가 분명하니 조항 단위로 자르고 상품명, 개정일, 조항 번호를 메타데이터로 붙여, 검색할 때 상품과 시점으로 먼저 거르겠습니다. 검색은 키워드와 벡터를 섞은 하이브리드 검색 뒤 리랭커로 순위를 다시 매기고, 답변에는 근거 조항을 함께 보여 줘서 현업이 바로 확인할 수 있게 하겠습니다.

- 메모: 시범 구축 경험(제목 기준 분할, 하이브리드, 리랭커)과 같은 구조라 「해 본 구성을 업무 문서에 맞게 바꾸면」으로 말한다.

**56. 하이브리드 검색과 리랭커는 왜 쓰나요?**

> 벡터 검색은 뜻이 비슷한 문장을 잘 찾지만, 상품명, 특약 이름, 조항 번호 같은 정확한 단어는 놓칠 수 있습니다. BM25 같은 키워드 검색이 그 빈틈을 메우고, 두 결과를 합친 뒤 질문과 문서를 함께 보는 리랭커가 상위 몇 개만 골라 생성 모델에 넘깁니다. 리랭커는 느리기 때문에 1차 검색으로 후보를 좁힌 뒤에만 씁니다.

**57. 표가 많은 문서는 어떻게 다루나요?**

> 표를 일반 텍스트처럼 자르면 행과 열의 관계가 깨집니다. 변환 단계에서 표를 구조로 뽑아 Markdown 표나 행 단위 문장으로 바꾸고, 표 제목과 바로 앞 설명을 같은 청크에 붙이겠습니다. 숫자를 계산해야 하는 질문은 생성 모델에 맡기지 않고 표 데이터를 직접 조회하는 쪽이 맞습니다.

**58. 환각, 즉 근거 없는 답은 어떻게 줄이나요?**

> 검색 단계와 생성 단계를 따로 다룹니다. 검색에서는 관련 문서가 충분히 높은 점수로 나오지 않으면 답하지 않고 「찾지 못했다」고 돌려주게 하고, 생성에서는 검색한 근거 안에서만 답하고 근거 조항을 인용하게 프롬프트와 출력 형식을 정합니다. 그리고 답이 근거와 맞는지 따로 검사하는 단계를 두겠습니다. 하네스에서 에이전트 결과를 판정 스크립트로 검사한 것과 같은 생각입니다.

**59. RAG 품질은 어떻게 평가하나요?**

> 질문과 정답 근거 문서, 기대 답변을 묶은 평가 세트를 현업과 함께 먼저 만듭니다. 검색은 정답 문서가 상위 k개 안에 드는 비율과 순위로 보고, 생성은 답이 근거에 충실한지, 질문에 맞는지를 사람 평가나 LLM 평가로 봅니다. 청크 크기, 임베딩 모델, 리랭커를 바꿀 때마다 같은 세트로 다시 돌려 비교합니다.

**60. RAG와 파인튜닝은 언제 각각 쓰나요?**

> 자주 바뀌는 사실과 근거를 보여 줘야 하는 지식은 RAG가 맞습니다. 약관이 개정되면 문서만 바꾸면 되고, 답의 출처를 보여 줄 수 있기 때문입니다. 파인튜닝은 답변 형식, 용어, 분류 같은 행동을 바꿀 때 쓰고, 금융권에서는 보통 RAG를 먼저 하고 부족한 부분만 LoRA 같은 가벼운 파인튜닝으로 보완합니다.

### 임베딩과 벡터 DB

**61. 임베딩 모델은 어떻게 고르나요?**

> 한국어와 업무 문서를 잘 다루는지, 긴 문서를 받을 수 있는지, 사내 장비에서 돌릴 수 있는 크기인지를 봅니다. 시범에서는 여러 언어를 지원하고 긴 입력을 받는 bge-m3를 썼습니다. 최종 선택은 우리 문서로 만든 평가 세트에서 검색 정확도를 비교해 정합니다.

**62. 벡터 DB로 pgvector와 전용 벡터 DB 중 무엇을 고르겠습니까?**

> 문서 수가 수백만 건 이하이고 이미 PostgreSQL을 운영한다면 pgvector가 운영 부담이 적습니다. 업무 데이터와 같은 DB에서 메타데이터 필터와 권한 조건을 SQL로 함께 걸 수 있다는 장점도 있습니다. 데이터가 훨씬 크거나 검색 지연 요구가 엄격하면 전용 벡터 DB를 검토합니다. 색인은 보통 HNSW를 쓰고, 정확도와 속도는 탐색 범위 설정으로 맞춥니다.

### 에이전트와 도구 연결

**63. 에이전트와 일반 LLM 호출, 워크플로는 무엇이 다른가요?**

> 일반 호출은 질문 하나에 답 하나입니다. 워크플로는 사람이 정한 순서대로 LLM과 도구를 부르고, 에이전트는 LLM이 다음에 어떤 도구를 쓸지 스스로 고르며 결과를 보고 반복합니다. 업무 서비스는 예측 가능해야 해서, 가능한 부분은 워크플로로 고정하고 판단이 필요한 구간에만 에이전트를 두는 것이 맞다고 봅니다. 하네스도 개발 루프의 순서는 고정하고 각 단계 안에서만 에이전트가 판단하게 했습니다.

**64. 도구 호출은 어떻게 동작하나요?**

> 도구의 이름, 설명, 입력 형식을 모델에 함께 넘기면, 모델이 필요할 때 어떤 도구를 어떤 인자로 부를지 구조화된 형식으로 답합니다. 애플리케이션이 실제로 그 도구를 실행하고 결과를 다시 모델에 넘기면, 모델이 그 결과로 답을 이어 가거나 다음 도구를 부릅니다. 이 반복을 언제 끝낼지, 어떤 도구를 허용할지는 애플리케이션이 통제합니다.

- 한계: 이 반복 루프를 API로 직접 짠 경험은 없다. 하네스에서는 Claude Code가 루프를 돌리고 도구는 스크립트 기반 MCP 도구로 만들어 붙였다. 「직접 짜 봤나」고 물으면 그렇게 답한다.

**65. MCP는 무엇이고 왜 쓰나요?**

> 모델 애플리케이션이 외부 도구와 데이터에 붙는 방식을 표준으로 정한 프로토콜입니다. 도구를 한 번 MCP 서버로 만들면 MCP를 지원하는 여러 에이전트와 애플리케이션에서 그대로 씁니다. 저는 SonarQube 조회, 지식베이스 검색, 제품별 빌드를 스크립트 기반 MCP 도구로 만들어 하네스에 붙였습니다.

### 보안과 금융 환경

**66. 금융권 AI 서비스에서 보안은 무엇을 먼저 보나요?**

> 개인정보와 권한입니다. 질문과 문서에 들어 있는 개인정보는 모델에 넘기기 전과 로그에 남기기 전에 마스킹하고, 사용자가 볼 권한이 없는 문서는 검색 단계에서 아예 빼야 합니다. 그리고 문서나 외부 입력에 숨은 지시로 모델이 엉뚱한 일을 하는 프롬프트 인젝션 위험을 줄이기 위해, 읽어 온 내용은 지시가 아니라 데이터로 다루고 모델이 쓸 수 있는 도구를 최소로 줍니다. 완전히 막을 수는 없다고 보고, 뚫려도 피해가 작도록 권한을 좁히는 것입니다.

- 메모: 하네스의 「외부에서 읽은 내용은 지시가 아닌 데이터로 취급」, 「에이전트별 도구 권한 제한」과 연결한다.

**67. 망분리 환경이면 개발 방식이 무엇이 달라지나요?**

> 외부 API와 인터넷 패키지를 바로 쓸 수 없습니다. 모델 가중치, 파이썬 패키지, 컨테이너 이미지를 반입 절차로 들여와 내부 저장소에 두고, 모델은 사내 GPU 서버에서 직접 서빙해야 합니다. 그래서 모델 버전과 패키지 버전을 고정해 관리하고, 반입 주기를 고려해 업데이트 계획을 세워야 합니다.

- 한계: 망분리 환경에서 일해 본 경험은 없다. 원리로만 답한다.

### 모델 서빙

**68. 온프레미스에서 LLM을 서빙할 때 vLLM을 쓰는 이유는 무엇인가요?**

> 같은 GPU에서 더 많은 요청을 처리하기 위해서입니다. vLLM은 PagedAttention으로 KV 캐시를 작은 블록 단위로 나눠 메모리 낭비를 줄이고, 연속 배칭으로 끝난 요청 자리에 새 요청을 바로 넣어 GPU를 계속 바쁘게 씁니다. OpenAI 호환 API를 제공해서 애플리케이션 코드를 바꾸지 않고 모델을 바꿔 끼우기도 쉽습니다.

**69. 8B 모델을 올리려면 GPU 메모리가 얼마나 필요한가요?**

> 가중치만 보면 16비트에서 파라미터 하나에 2바이트라 약 16GB가 필요하고, 4비트로 양자화하면 5GB 안팎입니다. 여기에 동시 요청 수와 문맥 길이에 비례하는 KV 캐시 메모리가 더 들기 때문에, 실제로는 가중치보다 넉넉한 여유를 두고 동시 사용자 수로 계산합니다. 같은 GPU에 임베딩 모델이나 리랭커를 함께 띄우면 그 몫을 빼고 남은 메모리로 KV 캐시를 계산합니다.

**70. 양자화를 하면 무엇을 얻고 무엇을 잃나요?**

> 메모리와 비용을 줄이고 더 큰 모델이나 더 많은 동시 요청을 같은 장비에 올릴 수 있습니다. 대신 정밀도가 낮아져 답변 품질이 떨어질 수 있어서, 8비트는 손실이 작은 편이고 4비트는 업무 평가 세트로 품질을 확인한 뒤 씁니다.

### 운영

**71. AI 서비스를 운영할 때 무엇을 지켜보나요?**

> 응답 지연, 특히 첫 토큰까지의 시간과 전체 응답 시간, 처리량과 오류율, GPU 사용률을 봅니다. 품질 쪽은 검색 결과가 비어 「찾지 못함」으로 끝난 질문, 사용자의 좋음과 나쁨 피드백, 답이 근거와 어긋난 사례를 모아 평가 세트에 다시 넣습니다. 하네스를 사용 기록으로 매주 고친 것처럼, 서비스도 기록으로 고도화 순서를 정합니다.

## 7. 협업, 상황, 마무리

### 협업과 상황

**72. 현업이 AI가 다 해 줄 거라고 기대할 때 어떻게 대응하겠습니까?**

> 처음에 할 수 있는 일과 없는 일을 업무 단위로 나눠 보여 드리겠습니다. 근거 문서를 찾아 요약하고 초안을 만드는 일은 맡기고, 최종 판단과 고객에게 나가는 내용은 사람이 확인하는 구조로 시작해 결과를 같이 보면서 범위를 넓히겠습니다. 하네스도 시작 승인과 최종 소스 검토는 사람이 맡게 경계를 정했습니다.

**73. 반대로 현업이 AI에 거부감을 가지거나 자기 일이 대체될까 걱정하면 어떻게 하겠습니까?**

**75. 일정이 부족한데 품질 기준을 낮추라는 요구를 받으면 어떻게 하나요?**

> 기준을 통째로 낮추지 않고, 반드시 지킬 것과 다음 릴리스로 미룰 것을 나눠서 제안합니다. 하네스에서도 변경 크기에 따라 리뷰 강도를 단계로 나눠, 작은 수정은 가벼운 검증만 거치고 위험한 변경에는 검증을 다 걸었습니다.

- 근거: 이력서 「리뷰 강도 단계화」.

**76. 입사하면 처음 3개월 동안 무엇을 하겠습니까?**

> 처음에는 이미 있는 AI 서비스와 사내 업무시스템, 데이터의 흐름을 파악하고, 현업이 매주 반복하는 일을 듣겠습니다. 그중 문서 검색이나 답변 초안처럼 효과가 바로 보이는 일 하나를 골라 평가 기준부터 같이 정하고, 작게 배포해 사용 기록으로 고치는 순서로 가겠습니다.

> 네, 괜찮습니다. 청라 근무를 전제로 준비하고 있습니다. (통근 방법을 한 문장 덧붙인다.)
