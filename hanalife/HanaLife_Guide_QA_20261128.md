## 1. 자기소개와 경력 이야기

### 자기소개와 강점

**1. 1분 자기소개를 해 주세요.**

> 원스토어 클라이언트개발팀에서 2023년부터 기술 리드를 맡고 있는 황보민입니다. 화려한 서비스는 아니지만, 올해 1월부터 Claude Code 위에 팀 AI 에이전트 하네스를 설계하고 구축해, 지금은 AI를 쓰지 않던 팀원까지 모두 이 환경에서 개발합니다. 에이전트는 끝났다고 말해도 그대로 믿기 어려워서 팀 규칙과 리뷰 기준을 하네스에 넣고 완료 여부는 검증 게이트가 판정하게 했고, 도입 뒤 QA 검증 기간 팀 결함이 이전의 절반 수준으로 줄었습니다. 이와 별도로 사내 장비에서 vLLM으로 sLLM을 서빙하는 RAG를 시범 구축했고, 그 전에는 원스토어, 제주항공, 뮤직메이트에서 대고객 앱과 웹을 만들어 왔습니다. 이 경험을 개발팀 한 곳이 아니라 회사 현업 업무 전반에 쓰는 자리라서 지원했습니다.

- 메모: 통화 21:35, G014. 가이드: 경민은 「화려하진 않지만 처음과 끝까지 에이전트를 만든 경험, 그걸로 팀 하네스를 조이고 리뷰 스타일을 잡았고, 해 보니 AI가 제멋대로 말해 하네스에 관심이 커졌고, 최근 팀 퍼포먼스를 올린 하네스를 열심히 했다」로 마무리하라고 함. 근거: 입력본 27, 136, 144, 185, 187, 212행, 이력서 9~13행. 가이드와 다르게 한 곳: 「처음부터 끝까지 에이전트를 만들었다」는 서류에 없어(도구 호출 루프 직접 구현 없음) 「Claude Code 위에 하네스를 구축했다」로, RAG는 하네스와 별도 시범으로 씀. 「제멋대로 말한다」는 서류의 「완료는 검증 게이트가 판정」으로 이음. 또 G014는 챗봇 이야기 뒤 하네스 순이고 「그 경험을 살려 하네스」로 잇지만, G008과 G016(AI 쪽은 하네스부터)에 따라 하네스를 앞에 두고, RAG 시범은 하네스와 별개라 인과로 잇지 않음(사실 규칙 6). 총 경력 연차 숫자는 넣지 않음.

### AI 에이전트 경험: 팀 하네스

**3. AI 에이전트 관련 경험을 말씀해 주세요.**

> 기술 리드로서 팀의 개발 성과를 올리려고 올해 1월부터 팀 AI 에이전트 하네스를 설계, 구축, 운영하고 있습니다. Jira 일감 하나를 넣으면 에이전트가 요구사항 분석, 계획, 테스트, 구현, 실기기 검증을 거쳐 PR 생성과 자동 리뷰까지 이어 가고, 사람은 지시와 검수를 맡는 구조입니다. AI를 쓰지 않던 팀원까지 지금은 전원이 이 환경에서 개발하고, 도입 뒤 QA 검증 기간 결함이 제 담당분은 0건, 팀은 이전의 절반 수준으로 줄었습니다.

- 메모: 통화 21:25, 21:27, G008. 가이드: 경민은 「테크리드로서 팀 퍼포먼스를 올리기 위해 하네스를 했다」로 에이전트 이야기의 첫 시작을 풀고 그것으로 점수를 따라고 함. 근거: 입력본 31~35행, 136행, 144행, 183행. 그 밖에: 통화 21:44 가이드(AI 쪽은 하네스로 팀 퍼포먼스를 올린 것부터, 기술 스택은 챗봇으로)는 이 묶음을 먼저 두고 RAG 시범 묶음을 뒤에 두는 순서로 반영.

**4. 팀에 하네스가 왜 필요했고, 본인은 어떤 역할을 했나요?**

> 팀원마다 에이전트를 각자 설정해 쓰면 코드 스타일, 계층 구조, Git 사용 방식이 사람마다 달라져서, 팀 전체의 기준을 맞춰 줄 사람이 필요했습니다. 저는 기술 리드로서 그 기준을 정하고 하네스로 옮겼습니다. 팀 규칙과 아키텍처 계층별 룰, 리뷰 기준과 가이드라인을 룰과 리뷰 에이전트에 넣고, 앱 저장소마다 아키텍처와 레거시 정보를 두어 코드와 함께 형상 관리하게 했습니다. 이것을 플러그인으로 묶어 배포해서 팀원 모두가 같은 환경에서 일합니다.

- 메모: 통화 21:25~21:26, G009. 가이드: 경민은 「Claude 같은 에이전트는 개성이 세서 커밋 스타일 등이 달라지니 팀에서 에이전트 전체의 균형을 맞춰 주는 사람이 있어야 한다」고 했고, 본인이 그 역할을 했다고 답함. 근거: 포트폴리오 74~77행, 81~82행, 95행, 101~102행, 입력본 49행. 본인 확인: 통화에서 말한 코드 맵 인덱싱과 빌드 전용 에이전트는 서류에 없어 넣지 않음(서류는 리뷰 기준과 가이드라인, 아키텍처 점검, 빌드 검증까지).

**5. 에이전트 쪽 경험을 좀 더 구체적으로 말씀해 주세요.**

> 하네스는 룰 11개, 역할별 에이전트 19개, 스킬 45개와 훅, MCP 서버로 이뤄져 있습니다. 늘 지켜야 할 팀 규칙은 상시 룰로, 아키텍처 계층별 규칙은 해당 경로를 건드릴 때만 읽히는 조건부 룰로 나눠 컨텍스트를 아끼고, 계획, 구현, 리뷰, 검증을 역할별 에이전트로 나눠 각자 필요한 도구만 쓰게 했습니다. 반복되는 업무는 팀원 작업 기록에서 찾아 스킬로 만들었고, 보호 브랜치나 위험 명령, 외부 전송은 훅으로 실행 전에 막습니다. 도구 쪽으로는 SonarQube 조회와 지식베이스 검색 MCP 서버를 Python으로 개발해 붙였습니다.

- 메모: 통화 21:29, G011. 가이드: 경민은 「팀 퍼포먼스를 위해 Claude나 Codex 하네스를 조정한 것, 스킬, 프롬프트 노하우로 에이전트 이야기를 풀고 RAG 같은 기술은 최대한 뒤로 빼라」고 함. 근거: 포트폴리오 74~93행, 이력서 149행, 입력본 39행, 141행. 가이드와 다르게 한 곳: Codex는 서류에 없고 통화에서도 「모두 Claude로 바꿨다」고 해 Claude Code만 씀. 정정: OpenAI 인터페이스 호환은 모델 호출 API 규격 이야기이고 훅, 스킬, 하위 에이전트 설정은 도구마다 달라 옮겨지는 것은 설계 방식뿐이라, 「지금 있는 에이전트에 똑같이 적용된다」는 말은 넣지 않음.

**6. 에이전트를 개발해 보셨어요? 무엇으로, 어떻게 하셨어요?**

> 에이전트 런타임을 직접 짠 것은 아니고, Claude Code 위에서 팀 전체가 쓰는 개발 에이전트 흐름을 설계해 만들었습니다. 워크플로가 Confluence 기획 문서를 분석해 표준 양식의 Jira 하위 일감을 만들고, 일감마다 계획, 테스트 먼저 작성, 구현, 빌드, 코드 리뷰, 실기기 시나리오 테스트를 차례로 돌리며, 검증 게이트에서 반려되면 구현부터 다시 합니다. 단계가 바뀔 때마다 Jira 일감에 코멘트가 자동으로 남아 PM이 에이전트 기록으로 진행을 파악하고, 단계마다 상태를 저장해 중간에 끊겨도 그 단계부터 이어 갑니다. 에이전트 정의와 워크플로 스킬은 Claude Code 설정으로 만들었습니다.

- 메모: 통화 22:29, 20:57, G023, G089. 가이드: 경민은 「전사에서 실행될 수 있는 하네스가 잡힌 에이전트를 만들어 봤다, 팀 내 전체에서 Jira 티켓도 끊고 해 봤다」고 답하라고 함(22:29). 20:57에는 「해 봤다고 하지 않고 LangGraph 붙일까 고민해 봤다고 대답하면 되겠다」는 말과 「에이전트 개발을 뭘로 했냐, 그냥 LangGraph로 했다, LangChain으로 했다」는 말이 섞여 나옴(화자 확정 안 됨). 근거: 포트폴리오 123~152행, 105행, 81~91행, 입력본 35행, 141행. 가이드와 다르게 한 곳: 「전사」는 서류상 클라이언트개발팀(9명) 단위라 「팀 전체」로 바꿈. 「LangGraph로 했다」는 서류에 없어 Claude Code로 쓰고, LangGraph를 검토하겠다는 판단은 4절 에이전트 프레임워크 묶음에서 답함. 그 밖에: 도구 호출 루프를 직접 구현하지 않아 「런타임을 직접 짠 것은 아니다」를 먼저 말함. Jira, Confluence 연결은 사내 MCP(포트폴리오 93행)라 내가 만든 MCP 서버는 SonarQube 조회와 지식베이스 검색 두 개로만 말하고, 그 문장은 앞 질문 「에이전트 쪽 경험을 좀 더 구체적으로」에만 둠. G023과 G089(4절 「그럼 에이전트 개발은 무엇으로 하셨어요?」)는 같은 질문이라 이 질문 하나로 합침.

**7. 코드는 직접 짜셨나요? 세부 구현은 어떻게 하셨어요?**

> 앱 기능 코드는 대부분 Claude Code로 작성합니다. 저는 구조와 의존 방향, 기능 배치를 정하고, 에이전트가 엉뚱한 작업을 하지 않는지와 결과가 기준을 지키는지를 봅니다. 그래서 테스트를 먼저 쓰게 하고 빌드, 리뷰, 실기기 검증을 통과해야 완료로 보는 장치를 하네스에 넣었습니다. MCP 서버, 훅, 개발 루프 실행기, push 전 게이트 같은 하네스 도구는 제가 설계하고 Python으로 직접 개발했습니다.

- 메모: 통화 21:47, 21:40, G017. 가이드: 경민은 「세세한 코드 작업은 AI, Claude 통해서 했다고 솔직하게 말하면 실무진이 납득하고, 대신 팀을 위해 하네스와 에이전트 세팅을 할 줄 안다는 점을 말하라」고 함. 근거: 포트폴리오 148~151행, 입력본 141행, 183행, 198행, 이력서 31행. 그 밖에: 앱 기능 구현을 에이전트가 맡는 것은 서류의 하네스 흐름(에이전트가 구현, 사람은 지시와 검수)과 같고, 하네스 도구는 서류대로 「Python으로 직접 개발」로 씀. 통화 21:40 본인 발언 「AI가 코드를 짜고 나는 감독」은 서류와 다름, 답에 쓰지 않음. 통화의 「1년 동안」, 「문법이 기억나지 않는다」는 넣지 않음.

### 서비스 쪽 AI 경험: RAG 시범

**8. 회사에서 LLM이나 에이전트를 직접 다뤄 본 적 있어요?**

> 두 가지가 있습니다. 하나는 앞서 말씀드린 팀 하네스로, Claude Code를 팀의 개발 업무와 사내 도구에 연결해 팀원 전원이 쓰고 있습니다. 다른 하나는 하네스와 별도로 한 RAG+sLLM 시범 구축으로, 사내 장비에서 vLLM으로 sLLM을 직접 서빙해 외부 API 없이 검색과 답변이 이어지게 했습니다. 상용 모델 위에서 에이전트를 통제하는 일과 작은 모델을 사내 자원으로 돌리는 일을 둘 다 해 봐서, 각각에서 비용과 한계가 어디서 생기는지 어느 정도 압니다.

- 메모: 통화 21:27~21:28, G010. 가이드: 경민은 하네스부터 말해 점수를 딴 뒤 「하네스 조정하면서 5090으로 에이전트와 RAG를 간단히 붙여 봤는데 결과가 좋지 않아 폐기됐고, 5090의 한계가 역력했지만 척박한 환경에서 하네스로 팀 퍼포먼스를 올리는 좋은 경험이 됐다」고 답하라고 함. 근거: 입력본 181행, 183행, 185행. 가이드와 다르게 한 곳: RAG는 하네스나 에이전트와 연결한 적이 없고 폐기도 서류에 없어 「하네스와 별도로 시범 구축」으로 씀. 그 밖에: 통화에서 본인이 말한 A2A, 머지, VOC 대응, 리뷰 5~6등급은 서류에 없어 넣지 않음.

**9. 이력서에 AI 에이전트라고 쓰셨는데, 백엔드에서 도는 에이전트를 만드신 건가요?**

> 아닙니다. 제가 만든 것은 Claude Code를 에이전트 실행 환경으로 쓰고 그 위에 팀 개발용 에이전트와 규칙, 도구를 얹은 하네스이고, 에이전트 루프 자체는 Claude Code가 제공합니다. 도구 호출, MCP, 컨텍스트 설계는 서비스형 에이전트와 같은 기술입니다. 단계별 상태 저장과 재개, 검증 루프는 워크플로 수준에서 설계해 본 것이고, 에이전트 루프와 대화 상태 관리를 서버에 직접 구현해 서비스로 띄우는 부분은 해 보지 않았습니다. RAG도 서비스로 운영한 것이 아니라 사내 장비에서 시범 구축한 수준이라고 이력서에 그대로 적었습니다.

- 메모: 통화 19:40, G002. 가이드: 경민은 「시범 구축 정도만 있으면 된다」, 하네스 위 개발 에이전트도 「플랫폼에서 도는 거랑 적용 기술 자체는 똑같다」고 함. 근거: 이력서 140~158행, 입력본 143행, 포트폴리오 105행. 정정: 공통점은 도구 호출, MCP, 컨텍스트 설계이고, 루프와 상태 관리, 서빙을 직접 구현한 백엔드 에이전트와 같은 경험이라고 하면 틀림. 하네스의 상태 저장과 재개는 워크플로 단계 상태라 에이전트 런타임의 대화 상태 체크포인트와 층위가 다름.

**10. 하네스 말고, 회사에서 직접 만들어 본 AI 서비스가 있나요?**

> 큰 서비스로 운영해 본 것은 아니고, 사내 장비에서 RAG+sLLM을 시범 구축했습니다. sLLM을 vLLM으로 서빙하고, 임베딩부터 검색, 리랭킹까지 외부 API 없이 사내 장비 안에서 이어지게 구성했습니다. 공고 우대 사항인 온프레미스 환경의 AI 서비스 구축과 가장 가까운 경험입니다.

- 메모: 통화 20:37, 21:33, G005, G013. 가이드: 경민은 「회사에 큰 거는 못 해 봤고 RAG 구축 시범을 했다, 회사가 5090 두 장을 사 줘서 한 장으로 사내 서비스를 만들라고 해서 만들었다」(20:37), 「POC 과제로 5090을 받아 챗봇을 만들었고, 에이전트는 LangGraph, DB는 Postgres 벡터 DB와 RDB를 연동해 RAG를 붙였다」(21:33)로 답하라고 함. 근거: 입력본 185행, 이력서 32행, 공고 39행. 가이드와 다르게 한 곳: 회사가 서비스나 POC 과제로 지시했다는 경위, GPU 대수, LangGraph, RDB 연동은 서류에 없어 빼고(LangGraph는 4절에서 안 써 봤다고 답함) 구성은 서류 범위로 씀. 검색 단계 세부(bge-m3, pgvector, 하이브리드 검색)는 3절 「시범에서 검색 앞단은」에만 두고 여기서는 줄임. RTX 5090: 제출 서류에 없음, 통화 20:00 본인 발언이라 3절 GPU 꼬리 질문에서만 말함. 본인 확인: 통화 20:01~20:02 본인은 한 장이라고 함(두 대는 동료 서비스와 경민 추측). 대수는 서류에 없어 답에 쓰지 않음. 본인 확인: 생성 모델 이름은 기록상 Qwen3-8B, 통화 20:39에는 Gemma라고 해 엇갈려 「sLLM」으로만 씀. 통화 21:31 가이드(실무진에는 하네스, 임원진에는 RAG 챗봇)에 따라 임원 면접에서는 이 답을 먼저 꺼냄.

**11. 그 시범은 어떤 용도였나요? 에이전트라고 볼 수 있나요?**

> 문서를 넣어 두고 질문하면 관련 내용을 찾아 답하는 질의응답 구성이었습니다. 흔히 챗 에이전트라고 부르는 형태지만, 도구를 골라 실행하며 사람 대신 일을 처리하는 에이전트가 아니라 검색해서 답하는 쪽입니다. 검색된 문서를 읽고 답하는 구성이라 사내 장비에 올라가는 작은 sLLM으로도 돌릴 수 있습니다.

- 메모: 통화 20:38, G006. 가이드: 경민은 「원스토어 앱 등록 규정을 지켰는지 확인하는 에이전트, 곧 규정집 보고 말하는 챗봇 에이전트를 5090 안에 들어갈 크기로 만들었다」고 말하라고 함. 근거: 입력본 185행. 가이드와 다르게 한 곳: 앱 등록 규정 챗봇은 서류에 없어 서류의 RAG 시범으로 바꾸고, 「사람 대신 행동하는 AI가 아니라 문서를 보고 말하는 챗 에이전트」라는 가이드의 구분은 살림. 본인 확인: 넣은 문서의 종류와 시범 용도는 서류에 없음. 그 밖에: 작은 모델을 고른 동기는 서류에 없어 셋째 문장은 일반론으로 씀.

### 모바일 개발자에서 AI 서비스 개발자로

**12. 모바일 경력이 대부분인데, AI 쪽 경험이 있나요?**

- 메모: 통화 22:14, G018. 가이드: 경민은 「모바일이나 코드로 너무 한정하지 말고, 팀 안에서 에이전트들이 조화롭게 실행되게 팀원과 설정을 조율할 줄 알아야 하며, 회사는 20명, 30명의 설정을 조정하는 일을 더 높게 산다」고 함. 근거: 입력본 187행, 189행, 220행, 포트폴리오 101행. 그 밖에: 경민 회사의 API 2,700개 사례는 경민 사례라 넣지 않고, 통화의 「모바일은 안 보인다」 같은 본인 평가도 넣지 않음.

**15. AI가 개발자를 대체한다는 말이 많은데, 본인 역할은 어떻게 보세요?**

> 코드를 치는 일은 AI로 많이 넘어가고 있지만, 무엇을 만들지 정하고 기준과 검증을 설계하는 일은 사람에게 남는다고 봅니다. 제 하네스도 에이전트가 분석부터 구현, 검증까지 하고 사람은 지시와 검수를 맡는 구조입니다. 그래서 제 역할을 에이전트가 일할 규칙과 완료 기준을 정하고, 결과가 그 기준을 지키는지 책임지는 사람으로 봅니다.

### 백엔드와 서버 경험

**16. 백엔드 경력은 이 직무와 어떻게 이어지나요?**

> 제주항공에서 모바일 웹의 여정, 운임 조회 백엔드를 Spring 3.1로, 서비스 콘텐츠 관리 시스템을 Spring Boot 2.x로 개발했습니다. 최근에는 하네스의 MCP 서버, 훅, 개발 루프 실행기를 Python으로 개발했습니다. 둘 다 요청을 받아 데이터를 처리하고 다른 시스템과 연결하는 코드라, 공고의 Python 백엔드로 AI 서비스 API를 만드는 일과 이어진다고 봅니다.

- 메모: 통화 19:44, G003. 가이드: 예전 백엔드와 제주항공 백엔드를 적어 서류가 통과됐다는 말에 경민이 「백엔드랑 에이전트랑 RAG가 지금 또 있고, CI/CD 쪽에 더 가까운 면모가 있다」고 평함. 근거: 입력본 86~87행, 141행, 공고 21행. 그 밖에: CI/CD 평은 가리키는 대상이 원문에서 불명해 넣지 않음. Node.js는 이력 미확인 항목이라 넣지 않음. Java 업무시스템과 Python AI 서버 연계 문장은 5절 「공고 요건 가운데 무엇을」 답과 겹쳐 지우고 그 답에만 둠(연계는 해 본 적 없다는 말도 그 답에 있음).

**17. 그래도 최근 경력에서 백엔드는 잘 안 보이는데요?**

> 맞습니다. 2020년 원스토어에 온 뒤로는 앱과 팀 하네스가 중심이었고, 서버 개발은 2018년부터 2020년까지 제주항공에서 모바일 웹 백엔드와 서비스 콘텐츠 관리 시스템을 만든 것이 가장 최근입니다. 더 앞서 공군 전산실에서는 인트라넷, 휴가 관리, 수송 배차 관리 웹 시스템을 Struts 1과 JSP로 화면부터 서버 로직, DB까지 만들었는데, 별도 API 계층 없이 서버 쪽 액션에서 DB를 바로 조회하는 구조였습니다. Python은 하네스의 MCP 서버와 도구를 만들며 쓰고 있고, REST API와 DB 설계 원칙은 언어가 바뀌어도 같다고 봅니다.

- 메모: 통화 21:36, G015. 가이드: 경민은 「서로 같이 알아가야 되고 너무 수준 높은 사람이 오는 걸 반기지 않을 수도 있다」, API 계층 없이 DB를 직접 조회하는 구조는 「지금도 많다」고 함. 근거: 입력본 86~87행, 175행, 199행, 이력서 234~236행. 본인 확인: 통화에서 「실제 백엔드는 군에서만」이라고 했지만 제출 서류는 제주항공 모바일 웹 백엔드와 콘텐츠 관리 시스템 개발을 적었으므로 서류대로 답하고, 맡은 API와 DB 범위는 면접 전에 정리. API 계층 없이 직접 조회한 구조는 제출 서류에 없음, 통화 21:37 본인 발언(「프론트에서」가 아니라 서버 쪽에서), 본인 확인.

**18. 백엔드나 서버 환경은 어느 정도 아세요?**

> 제주항공에서 여정, 운임 조회처럼 접속이 몰리는 화면의 백엔드와 서비스 콘텐츠 관리 시스템을 만들어서, 서버가 어떤 요청을 처리하고 관리 화면이 어떻게 붙는지는 대화가 통하는 수준으로 압니다. 공군 전산실에서는 Tomcat과 Apache로 웹 서버와 DB를 운영했습니다. 지금은 코드를 다 직접 치기보다 에이전트에게 지시하고 결과를 검수하는 방식이라, 구조를 설명하고 설정이 엉뚱한 데로 가지 않게 잡는 쪽에 강점이 있습니다.

## 2. RAG, 검색, 데이터베이스

### RAG 개념

**22. RAG가 무엇인가요? 약자도 말씀해 주세요.**

> RAG는 Retrieval-Augmented Generation의 약자로, 검색 증강 생성이라고 부릅니다. 모델이 학습하지 않은 사내 문서 같은 지식을 질문할 때마다 검색해서 프롬프트에 넣어 주고, 모델은 그 내용을 바탕으로 답하는 방식입니다. RAG 자체는 저장소가 아니라 방식이고, 문서를 벡터로 바꿔 담아 두는 곳은 벡터 DB입니다. 모델을 다시 학습시키지 않아도 문서만 바꾸면 최신 내용으로 답할 수 있다는 점이 장점입니다.

- 메모: 통화 20:07, G025. 가이드: 경민은 RAG를 문장을 벡터로 바꿔 저장한 「말뭉치 저장소」로, 약자를 「Retrieval Augmented Graph」로 설명. 근거: 경력 사실 없음, 기술 설명. 정정: G는 그래프가 아니라 Generation이고, RAG는 저장소가 아니라 방식이며 저장소는 벡터 DB, LLM은 그래프가 아니라 트랜스포머 구조의 신경망.

**23. RAG는 어떤 단계로 처리되나요?**

> 검색, 증강, 생성의 세 단계로 설명합니다. 질문이 들어오면 관련 문서 조각을 찾고, 찾은 내용을 질문과 함께 프롬프트에 넣고, LLM이 그 내용을 근거로 답을 만듭니다. 그 앞에는 문서를 잘라 임베딩하고 벡터 DB에 적재하는 준비 단계가 따로 있습니다. 제 시범은 이 흐름의 검색 단계에 하이브리드 검색과 리랭킹을 더한 구성이었습니다.

- 메모: 통화 19:41, G024. 가이드: 경민은 「RAG는 단순하고 그냥 RAG라고 부른다, 몇 단계인지는 4~5년 전이라 기억나지 않는다」고 넘김. 근거: 입력본 185행. 정정: 표준 설명은 검색, 증강, 생성의 세 단계.

**24. 그럼 RAG로 회사 데이터를 학습시키는 건가요?**

> 아닙니다, RAG는 모델을 학습시키지 않고 조회하는 방식입니다. 모델 가중치는 그대로 두고, 질문이 올 때 문서를 검색해 컨텍스트로 넣어 줄 뿐입니다. 제 시범도 모델은 손대지 않고 검색 쪽만 구성했습니다.

- 메모: 통화 20:19, G033. 가이드: 본인이 「회사 데이터로 RAG를 학습시킨다」고 말하자 경민이 「RAG를 학습시키는 게 아니라 조회하는 것」이라고 바로잡음. 근거: 입력본 185행(서류에 파인튜닝 없음). 정정: 「RAG를 학습시켰다」고 말하면 틀림. 그 밖에: 파인튜닝을 언제 쓰는지는 3절 파인튜닝 묶음과 겹쳐 여기서는 뺌.

### 임베딩과 인덱싱

**25. 임베딩이 무엇이고, LLM이나 RAG 데이터와는 어떤 관계인가요?**

> 임베딩은 텍스트를 의미가 담긴 고정 길이 숫자 벡터로 바꾸는 것이고, 뜻이 비슷한 텍스트는 벡터 공간에서 가깝게 놓입니다. 이 일은 답을 만드는 생성 모델이 아니라 임베딩 전용 모델이 하는데, 제 시범에서 쓴 bge-m3는 텍스트 조각 하나를 1024차원 벡터로 바꿉니다. 그래서 생성 모델의 파라미터 수와 벡터 DB 크기는 관계가 없고, 벡터 DB 크기는 저장한 청크 수와 임베딩 차원으로 정해집니다. LLM과 RAG 데이터는 검색된 원문이 프롬프트에 들어갈 때 처음 만납니다.

- 메모: 통화 20:08, 20:24, 20:36, G026. 가이드: 경민은 임베딩을 포인터에 비유하고, 26B 모델이면 260억 개 포인터가 있고 RAG에도 26B 크기가 1대1로 대응한다고 설명. 근거: 입력본 185행(bge-m3). 정정: 파라미터 수는 임베딩 차원, 벡터 DB 저장 건수, 컨텍스트 길이, 말뭉치 크기와 대응하지 않음. 26B 모델을 올릴 때 드는 것은 가중치 메모리로 FP16 기준 약 52GB.

**26. 임베딩과 인덱싱은 어떻게 다른가요?**

> 임베딩은 텍스트를 벡터로 바꾸는 한 단계만 가리키고, 인덱싱은 그 앞뒤를 포함한 적재 과정 전체를 말합니다. 문서에서 텍스트를 뽑고, 적당한 길이로 청킹하고, 청크마다 임베딩한 뒤, 원문과 메타데이터와 함께 벡터 DB에 넣고 검색용 인덱스를 만드는 것까지가 인덱싱 파이프라인입니다. 현장에서는 이 과정을 통틀어 임베딩한다고 부르기도 하는데, 검색이 틀렸을 때 청킹 문제인지 임베딩 모델 문제인지 나눠 봐야 해서 저는 구분해서 씁니다.

- 메모: 통화 20:14, G030. 가이드: 경민은 「인덱스 자르는 거, 문자 자르는 거, PDF 밀어 넣는 거, RAG에 들어가는 건 다 임베딩이라고 부른다」고 함. 근거: 경력 사실 없음, 기술 설명. 정정: 임베딩은 벡터 변환 단계만 가리키고, 청킹부터 벡터 DB 적재까지는 인덱싱 파이프라인.

**27. 임베딩 모델은 무엇이고, 검색 결과가 맞는지는 어떻게 확인하나요?**

> 임베딩 모델은 텍스트를 벡터로만 바꿔 주는 별도 모델이고, 앞서 말씀드린 bge-m3가 그런 모델입니다. 벡터 숫자만 보면 무엇이 들었는지 알 수 없지만, 벡터 DB에는 벡터와 함께 원문 청크와 문서 정보를 같이 저장하니 검색 결과는 원문으로 바로 확인할 수 있습니다. 검색 품질 자체는 질문과 정답 문서를 짝지은 평가 세트를 만들어, 상위 몇 건 안에 정답 문서가 들어오는 비율로 재는 것이 맞다고 봅니다.

- 메모: 통화 20:26, G037. 가이드: 경민은 「임베딩만 계산하는 모델이 따로 있고 벡터만 찍어 준다」고 했고, 그 벡터만 보고는 찾아온 게 맞는지 알 수 없다는 점이 문제로 나옴. 근거: 입력본 185행. 정정: 원문 청크를 함께 저장하므로 원문으로 확인할 수 있고, 품질은 평가 세트로 잼. 본인 확인: 통화에서 「임베딩 모델을 컴퓨터에 설치해 해 봤다」고 한 것이 사내 장비 시범과 같은 구성인지, 시범에서 평가 세트로 검색 품질을 쟀는지(서류에 없음).

### 리랭킹

**28. 리랭킹이 무엇인가요?**

> 리랭킹은 검색기가 가져온 후보 청크를, 답을 만들기 전에 질문과의 관련도로 다시 점수 매겨 순서를 바꾸는 단계입니다. 1차 검색은 질문과 문서를 따로 임베딩해 빠르게 비교하는 대신 정밀도가 떨어지는데, 리랭커는 크로스 인코더처럼 질문과 문서를 한 쌍으로 넣어 더 정확하게 봅니다. 순서는 질문 임베딩, 벡터 DB 검색, 리랭킹, 프롬프트 구성, 답변 생성입니다. 생성 결과가 마음에 안 들 때 여러 번 다시 돌리는 것과는 다른 단계입니다.

- 메모: 통화 20:09~20:10, G027. 가이드: 경민은 리랭킹을 「랭크가 안 좋아 뒤에서 보정하는 것, 마음에 드는 게 안 나오면 100번 돌려 찾게 하는 것」으로, 한 번에 잘 나오는 것을 「원 핫 프롬프트」로 설명. 근거: 경력 사실 없음, 기술 설명. 정정: 리랭킹은 생성 전에 후보 순서를 다시 매기는 단계이고, 원핫 인코딩은 범주 하나만 1로 표시한 벡터 표현이며, 예시 하나를 주고 답하게 하는 것은 원샷, 예시 없이는 제로샷 프롬프팅.

**29. 리랭킹을 써 보셨어요?**

> 네, RAG 시범에서 하이브리드 검색 뒤에 리랭커를 붙여 구성했습니다. 리랭커는 후보마다 질문과 함께 모델을 한 번씩 더 돌리는 구조라 후보 수만큼 응답 시간과 GPU 연산이 늘어납니다. 그래서 1차 검색에서 후보를 상위 몇십 건으로 줄인 다음에 거는 것이 맞고, 앞단 검색만으로 순위가 충분히 나오면 꺼서 비용을 아끼는 선택도 할 수 있는 단계라고 봅니다.

- 메모: 통화 20:11, G028. 가이드: 경민은 「개발할 때 리랭킹을 끄고 쓴다, 대신 프롬프트나 하네스를 조정한다」고 답하라고 함. 근거: 입력본 143행, 185행. 가이드와 다르게 한 곳: 서류에 리랭킹을 구성했다고 적혀 있어 「끄고 쓴다」를 「시범에서 리랭커를 구성했다」로 바꾸고, 비용을 의식하는 태도는 「꺼서 비용을 아끼는 선택」으로 살림. 정정: 비용 근거는 「100번 재실행」이 아니라 리랭커 추론의 지연 시간과 연산. 본인 확인: 리랭커 모델 이름과 후보 수는 서류에 없음.

**30. 실무에서 리랭킹은 어떻게 생각하세요?**

> 효과는 확실하지만 비용이 드는 단계라, 앞단을 먼저 다듬는 쪽을 더 좋아합니다. 청크를 문단 단위로 자르고, 문서 종류나 시행일 같은 메타데이터를 붙이고, 키워드와 벡터를 섞어 1차 후보 품질을 올리면 리랭커가 할 일이 줄어듭니다. 그래도 상위 순위가 흔들리거나 일정이 촉박하면 리랭커를 켜고 먼저 내보낸 뒤, 앞단을 고쳐 가며 끌 수 있는지 보는 것이 맞다고 봅니다.

- 메모: 통화 20:13, G029. 가이드: 경민은 「리랭킹 알죠, 근데 하네스나 RAG에 데이터를 더 잘 쌓는 방법을 더 좋아하고, 리랭킹은 최후에 안 나오거나 시간이 촉박할 때 켜고 나갈 수 있다」고 답하라고 함. 근거: 경력 사실 없음, 판단. 정정: 리랭킹은 검색 단계, 하네스는 에이전트 실행 환경이라 서로 대신하지 않으므로 하네스 대목은 빼고 데이터를 잘 쌓는 쪽만 살림. 그 밖에: 경민 회사가 H100을 나눠 쓰며 리랭킹을 끈다는 것은 경민 사례라 넣지 않음.

### RAG의 한계와 롱 컨텍스트

**31. 요즘 RAG는 어떻게 보세요? 한계가 뭐라고 생각하세요?**

> RAG는 지금도 사내 문서 검색과 상담 챗봇에서 가장 널리 쓰는 방식이라고 봅니다. 한계는 검색이 틀리면 모델이 아무리 좋아도 답이 틀린다는 점이고, 청크가 잘못 잘리거나 상품 코드 같은 정확한 키워드를 벡터 검색이 놓치는 경우가 대표적입니다. 그래서 청킹과 메타데이터를 다듬고, 키워드 검색을 섞은 하이브리드 검색과 리랭킹으로 보완하는데, 제 시범에도 그 두 가지를 넣었습니다.

- 메모: 통화 20:23, G034. 가이드: 본인이 「요즘 RAG는 정확도가 떨어져 안 쓴다고 들었다」고 하자 경민이 「맞다, 현업에서도 그렇게 안다」고 함. 근거: 입력본 185행. 정정: RAG는 지금도 널리 쓰고 정확도는 청킹, 하이브리드 검색, 리랭킹으로 보완하며, 「요즘 안 쓴다」고 하면 RAG 시범을 적은 서류와도 어긋남.

**32. 문서를 컨텍스트에 통째로 넣는 방식과 RAG는 언제 각각 고르시나요?**

> 문서가 적고 한 번에 다 읽혀야 하는 일이면 컨텍스트에 통째로 넣고, 문서가 많거나 자주 바뀌면 RAG를 고릅니다. 예를 들어 새로 나온 규정 문서 몇 개를 요약하거나 비교하는 일은 통째로 넣는 쪽이 빠르고 정확합니다. 반대로 몇 년치 사내 문서에서 질문마다 필요한 부분을 찾아야 하면 모델의 컨텍스트 창 길이를 넘고, 자체 서빙이면 그만큼 GPU 메모리와 응답 시간도 늘어나서 RAG로 필요한 청크만 넣는 편이 맞습니다.

- 메모: 통화 20:15, 20:26~20:27, G031. 가이드: 경민은 RAG를 「임베딩 서치」, 통째로 넣는 방식을 「LLM 서치」라 부르고, 정부 규정 15개 요약은 통째로, 10년치 기업 문서 온보딩 챗봇은 RAG라는 예를 듦. 근거: 경력 사실 없음, 판단. 정정: 표준 용어는 롱 컨텍스트 방식과 RAG의 벡터 검색이고, 롱 컨텍스트의 한계는 먼저 컨텍스트 창 길이이며, 임베딩 차원은 수백에서 수천이지 1억 차원이 아님.

**33. RAG 검색이 잘 안 되는 이유는 뭐라고 보세요?**

> 벡터 검색은 뜻이 비슷한 것은 잘 찾지만, 조항 번호나 상품 코드처럼 글자가 정확히 맞아야 하는 질문에 약합니다. 「apple」 같은 다의어는 임베딩 모델이 청크의 앞뒤 문맥까지 담아 벡터를 만들기 때문에 어느 정도는 구분합니다. 그래서 정확한 키워드는 BM25 같은 키워드 검색이, 의미가 비슷한 문장은 벡터 검색이 맡도록 섞는 하이브리드 검색으로 보완하고, 청크 경계에서 내용이 끊기는 문제는 청크를 겹쳐 자르는 식으로 줄입니다.

- 메모: 통화 20:24, G035. 가이드: 경민은 「큰 저장소에 들어가면 인덱스를 못 찾고, apple이 기업, 과일, 뉴욕 중 무엇인지가 문제」라고 설명. 근거: 경력 사실 없음, 기술 설명. 정정: 다의어는 문맥 임베딩으로 어느 정도 구분하고, 벡터 검색의 약점은 정확한 키워드라 하이브리드 검색으로 보완.

**34. 벡터 DB에 잘못 들어간 데이터는 어떻게 처리하나요?**

> 청크마다 원문과 문서 ID, 버전 같은 메타데이터를 함께 저장해 두면, 잘못 들어간 문서의 청크만 골라 지우고 다시 임베딩해 넣으면 됩니다. 전부 지우고 새로 쌓을 필요는 없고, 문서가 개정될 때도 같은 방식으로 그 문서만 갈아 끼웁니다. 그래서 처음 적재를 설계할 때 문서 ID와 출처를 청크에 꼭 남기는 것이 중요하다고 봅니다.

- 메모: 통화 20:25, G036. 가이드: 경민은 「한 번 잘못 들어가 잘못 응답하기 시작하면 도저히 못 찾으니, 지우고 새로 쌓는 게 더 빠르다」고 함. 근거: 경력 사실 없음, 기술 설명. 정정: 메타데이터로 해당 문서의 청크만 지우고 다시 임베딩하면 되고, 전부 새로 쌓아야 한다고 하면 틀림.

### 벡터 저장소와 PostgreSQL

**35. 벡터 DB는 무엇으로 구축하나요? 사내에서 모델을 돌리는 구성과 외부 모델을 쓰는 구성은 무엇이 다른가요?**

> 벡터 타입과 유사도 검색을 지원하는 DB면 되고, PostgreSQL에 pgvector 확장을 얹는 방법이 가장 간단합니다. 문서 검색과 프롬프트 구성까지는 두 구성이 같고, 차이는 생성 모델을 사내 GPU에서 vLLM 같은 서빙 엔진으로 돌리느냐, 외부 API로 부르느냐입니다. 외부 API를 쓰면 검색된 사내 문서가 프롬프트에 실려 밖으로 나가므로, 망분리나 금융권 환경에서는 사내 서빙이 필요합니다. 제 시범은 사내 장비에서 vLLM으로 sLLM을 서빙하고, 임베딩부터 리랭킹까지 외부 API 없이 이어지게 구성했습니다.

- 메모: 통화 20:17, G032. 가이드: 경민은 「따로 구축이랄 것도 없이 PostgreSQL을 깔아도 되고, 차이는 그 LLM이 온프레미스냐 Claude냐」라고 함. 근거: 입력본 185행, 이력서 32행. 그 밖에: 통화에서 본인이 「내 Claude 환경도 추론 서버만 밖에 있고 나머지는 RAG와 비슷하지 않냐」고 물은 대목은 층위가 달라(하네스는 에이전트 실행 환경, 서류상 RAG와 연결한 적 없음) 답에 넣지 않음.

**36. pgvector는 어떻게 동작하나요? 벡터와 일반 데이터가 따로 있나요?**

> 따로 있지 않습니다. pgvector는 PostgreSQL 테이블에 vector 열 타입과 거리 연산자, 그리고 HNSW나 IVFFlat 같은 벡터 인덱스를 추가하는 확장입니다. 그래서 한 테이블에 원문, 문서 ID, 카테고리 같은 일반 열과 벡터 열을 같이 두고, 한 SQL 문으로 조건을 걸면서 거리순으로 정렬해 가져올 수 있습니다.

- 메모: 통화 20:31, G041. 가이드: 「벡터와 RDB는 따로 동작하고 관계 연결은 익스텐션이 지원한다」는 정리에 경민이 「서치도 셀렉트도 다 지원해 줘서 편해서 쓴다」고 함. 근거: 경력 사실 없음, 기술 설명. 정정: 벡터는 같은 테이블의 열로 들어가고 한 SQL로 함께 조회함.

**37. 벡터 저장소로 PostgreSQL을 쓰면 무엇이 좋은가요?**

> 가장 큰 장점은 메타데이터 필터링입니다. 예를 들어 상품 종류나 문서 유형, 시행일로 먼저 범위를 좁히고 그 안에서만 유사도 검색을 하면, 엉뚱한 상품의 문서가 섞여 나오는 일이 줄어듭니다. 현업 개발자에게서도 벡터를 넣을 때 카테고리를 표시해 두고 찾을 때 범위를 좁힌다고 들었습니다. 벡터 전용 DB를 따로 운영하지 않아도 되고, 백업과 권한 관리를 기존 DB 운영 방식대로 가져갈 수 있다는 점도 장점입니다.

- 메모: 통화 20:30, G040. 가이드: 경민은 pgvector가 들어간 PostgreSQL에 임베딩을 다 넣고, RDB에 카테고리를 마킹해 찾는 범위를 좁힌다며 「벡터도 되고 RDB도 되니 1타 쌍피」라고 함. 근거: 경력 사실 없음, 기술 설명. 그 밖에: 경민 사례는 정리 md 기준대로 「현업 개발자에게 들은 사례」로만 인용하고 표준 용어 메타데이터 필터링으로 씀. 「한 테이블에 두고 SQL로」 설명은 「pgvector는 어떻게 동작하나요?」에만 둠. 정정: Chroma는 구글 제품이 아니라 오픈소스 벡터 DB.

### 시범의 지식 처리와 저장소 선택

**38. 시범에서 문서, 곧 지식은 어떻게 넣으셨고 저장소는 무엇을 쓰셨어요?**

> 문서를 bge-m3로 임베딩해 PostgreSQL의 pgvector에 저장했습니다. pgvector는 PostgreSQL에 벡터 검색을 더하는 오픈소스 확장이라 라이선스 비용이 없습니다. 문서가 몇 개 안 되면 컨텍스트에 통째로 넣는 편이 빠르지만, 찾아야 할 문서가 늘어나면 이렇게 검색해서 필요한 부분만 넣는 구성이 필요합니다.

- 메모: 통화 20:40~20:41, G044. 가이드: 경민은 「규정집은 처음에 LLM에 넣어 찾다가 문서가 많아 RAG에 넣었고, DB는 회사에 널린 PostgreSQL, pgvector는 공짜 오픈소스라 유지보수 지원도 된다」고 답하라고 함. 근거: 입력본 143행, 185행. 가이드와 다르게 한 곳: 규정집, 롱 컨텍스트에서 RAG로 옮긴 과정, 회사에 이미 있던 PostgreSQL은 서류에 없어 빼고, 롱 컨텍스트와 RAG의 선택 기준은 판단으로만 말함. 정정: 오픈소스라고 유지보수 지원이 따라오지는 않아 「라이선스 비용이 없다」까지만 씀. 그 밖에: pgvector를 고른 동기는 서류에 없어 「쓴 것은 ~때문」 같은 선택 이유로 말하지 않고 일반 설명으로 씀. 「한 테이블에서 SQL로」 설명은 「pgvector는 어떻게 동작하나요?」에만 둠. 본인 확인: 넣은 문서의 종류와 양, pgvector를 고른 이유(서류에 없음). 기록상 pgvector는 Docker 컨테이너로 따로 띄웠으므로(서류에 없음) 「기존 PostgreSQL에 확장 하나 설치」로 말하지 않음.

**39. Elasticsearch나 Redis 같은 다른 DB는 어떻게 보세요? 대화 이력은 어디에 두시겠어요?**

> Elasticsearch도 벡터 검색과 하이브리드 검색을 지원해 벡터 저장소로 쓸 수 있고, Redis도 벡터 검색 기능이 있지만 주로 캐시로 붙이며, 그래프 DB는 관계 탐색용입니다. 이미 키워드 검색에 Elasticsearch를 쓰는 곳이면 그 안에서 벡터까지 처리하는 선택도 있습니다. 지식 데이터가 많지 않으면 PostgreSQL과 pgvector로 충분하고, 서비스로 만든다면 대화 이력도 세션 ID 기준으로 같은 PostgreSQL의 일반 테이블에 두어 DB 하나로 운영하겠습니다.

- 메모: 통화 21:34, G053. 가이드: 경민은 「DB와 RDB가 필요해 Elasticsearch에 Redis를 붙이는 방법, 다 합쳐진 그래프 DB도 찾아봤지만 설치된 PostgreSQL 안에서 해결했고, 채팅 이력은 RDB에, 지식은 양이 많지 않아 PostgreSQL에 쌓았다」고 말하라고 함. 근거: 입력본 143행. 가이드와 다르게 한 곳: 검토 과정, 이미 설치된 PostgreSQL, 채팅 이력 RDB 저장은 서류에 없어 경험이 아니라 판단으로 바꿈. 정정: 그래프 DB는 노드와 관계를 저장, 탐색하는 DB라 전문 검색, 캐시, 관계형 저장을 합친 것이 아님. Elasticsearch는 dense_vector 필드와 kNN 검색, BM25와 벡터를 합치는 하이브리드 검색을 지원하고 Redis에도 벡터 검색 기능이 있어, 둘이 벡터 저장소를 대신하지 못한다고 하면 틀림. 그 밖에: 「한 테이블에 벡터와 원문, 메타데이터」 설명은 「pgvector는 어떻게 동작하나요?」에만 둠. 본인 확인: 시범의 대화 이력 처리는 서류에 없어 답에 쓰지 않음(기록상 조립에 쓴 Open WebUI가 관리).

**40. LLM이 좋아지면 검색 단계 없이 다 맡기면 되지 않나요?**

> 그래도 검색 단계는 모델이 바뀌어도 남는 자산이라고 봅니다. 공개 모델 성능이 빠르게 오르고 있어서 시간이 지나면 폐쇄망 안에서도 지금보다 훨씬 좋은 모델을 돌릴 수 있을 텐데, 그때도 모델은 사내 문서를 모르니 키워드 검색, 벡터 검색, 메타데이터로 쌓아 둔 색인은 그대로 필요합니다. 검색과 생성 모델을 나눠 두면 나중에는 모델만 갈아 끼우면 되고, 그 사이 사내 검색 엔진처럼 쓰이는 기반이 먼저 쌓입니다. 제 시범도 검색 단계와 sLLM 서빙을 나눠 외부 API 없이 이어지게 구성했습니다.

- 메모: 통화 21:21, G050. 가이드: 경민은 「왜 그렇게 했냐, 왜 PostgreSQL이냐」에 「시간이 지나면 폐쇄망에서도 LLM이 잘 도는 환경이 오고, 키워드와 의미 유사도 검색 단계를 쌓아 두면 나중에 에이전트만 갈아 끼워 사내 네이버, 사내 구글이 된다」는 논리로 답하라고 함. 근거: 입력본 185행. 가이드와 다르게 한 곳: 「그걸 내다보고 구성했다」는 동기는 서류에 없어 판단으로 말하고, 구성 사실은 서류 범위로. 정정: 상용 모델을 써도 모델은 사내 데이터를 모르므로 검색 색인은 여전히 필요(정리 md 21:22 정정 줄).

### LLM 호출을 줄이는 검색 순서

**41. 룰베이스는 무엇이고 키워드 검색과 어떻게 다른가요?**

> 룰베이스는 사람이 정한 조건문, 사전, 정규식 같은 규칙으로 판단하고 처리하는 방식이고, 키워드 검색은 질문의 단어가 들어 있는 문서를 BM25 같은 점수로 찾아 순위를 매기는 검색 방식이라 같은 말이 아닙니다. 룰베이스는 규칙에 맞으면 정해진 처리를 끝까지 하고, 키워드 검색은 후보 문서를 가져오는 데까지라 둘을 같이 쓰는 경우가 많습니다. 예를 들어 질문에 상품 코드가 있으면 정규식으로 뽑아 바로 조회하고, 규칙으로 안 풀리는 질문만 검색과 LLM으로 넘기면 LLM 호출 수가 줄어듭니다.

- 메모: 통화 21:07~21:09, G045. 가이드: 경민은 「LLM은 돈이 드니 일단 배제하고 콜을 최대한 줄인다, 룰베이스는 이프문의 향연이고 키워드 서치와 같은 말」이라고 함. 근거: 경력 사실 없음, 판단. 그 밖에: LLM 호출 비용과 지연 이야기는 3절 「실무에서 LLM 호출을 줄이려는 이유는 무엇인가요?」와 겹쳐 그 답에 맡기고, 이 질문은 룰베이스와 키워드 검색의 차이로 바꿈. 정정: 룰베이스와 키워드 검색은 같은 말이 아니고, 룰베이스와 하네스도 다른 것이며, 멀티모달 모델은 이미지를 글로 번역하지 않고 이미지 인코더로 토큰화해 처리함.

**42. 키워드 검색은 어디서 어떻게 돌고, LLM 없이 자연어 질문은 어떻게 처리하나요?**

> 키워드 검색은 백엔드의 검색 엔진, 예를 들어 Elasticsearch가 BM25 점수로 처리하고, 그 결과를 LLM 컨텍스트로 넘깁니다. 자연어 질문은 형태소 분석기로 조사, 어미, 문장 부호를 떼고 명사 같은 핵심어만 남겨 검색어로 쓰면 LLM 없이도 상당 부분 처리됩니다. 한국어는 Elasticsearch의 Nori 같은 한국어 형태소 분석기를 붙여야 이 처리가 제대로 됩니다. 「2025년 변액보험 약관 찾아 줘」처럼 질문 안에 키워드가 들어 있는 경우가 많아서, 이 단계에서 끝나는 질문도 꽤 됩니다.

- 메모: 통화 21:09~21:11, G046. 가이드: 경민은 주소를 서울시, 관악구, 낙성대, 시장 순으로 좁히는 예를 들고, 찾는 곳은 백엔드이며 「형태소 분석기로 부사, 조사, 동사를 떼면 명사만 남아 AI 없이 찾는다」고 함. 근거: 경력 사실 없음, 기술 설명. 정정: 한국어 기본 어순은 SVO가 아니라 SOV. 그 밖에: 가이드의 「국가보훈처」 예는 기관명이 바뀌어 보험 예로 바꿈.

**43. 키워드 검색 다음은 뭔가요? 임베딩 검색은 AI 없이 되나요?**

> 다음은 의미 유사도로 찾는 벡터 검색인데, 이것도 질문을 벡터로 바꾸는 임베딩 모델 추론이 필요하니 AI가 전혀 없는 것은 아닙니다. 정확히는 생성형 LLM 호출 없이 된다고 말하는 게 맞고, 시범에서 쓴 bge-m3 같은 임베딩 모델은 생성 모델보다 훨씬 작고 빨라 비용 부담이 적습니다. 질문과 문서를 같은 임베딩 모델로 벡터화하고, 거리 계산은 pgvector 같은 벡터 DB가 맡는 구조입니다.

- 메모: 통화 21:13~21:14, G047. 가이드: 경민은 「키워드 다음은 RAG DB의 임베딩 서치이고 여기도 LLM에 안 넣어도 되니 AI를 안 써도 된다, 지금 AI를 안 쓰는 방법만 먼저 이야기하는 것」이라고 함. 근거: 입력본 185행. 정정: 임베딩 검색에도 임베딩 모델 추론이 필요하므로 「AI 없이」가 아니라 「생성형 LLM 호출 없이」. 그 밖에: 「하나」로 찾으면 하나은행이 묶여 나온다는 예는 단어 하나짜리 질의에서 보장되지 않아 넣지 않음.

**44. 검색 정확도는 어떻게 올리고, LLM은 어느 단계에 넣으세요?**

> 키워드 검색과 벡터 검색을 섞는 하이브리드 검색으로 정확도를 올리고, LLM은 맨 마지막 답변 생성에 넣습니다. 다만 BM25 점수와 벡터 유사도는 척도가 달라 0.4, 0.6처럼 그대로 더하면 안 되고, 정규화한 뒤 가중합하거나 순위만 합치는 RRF를 씁니다. 그렇게 상위 k건을 뽑아 리랭킹으로 순서를 다듬은 뒤 LLM에 넘기는데, 제 시범도 하이브리드 검색, 리랭킹, sLLM 순으로 이었습니다. 리랭킹까지는 생성형 LLM을 부르지 않으니 생성 호출은 질문당 한 번으로 묶이고, 임베딩과 리랭커 추론은 그보다 훨씬 가볍습니다.

- 메모: 통화 21:17, G048. 가이드: 경민은 「키워드 서치, 안 되면 룰에 키워드 추가, 안 되면 의미 유사도, 안 되면 키워드 0.4, 의미 0.6으로 섞어 TOPK 10개, AI는 맨 마지막」이라고 정리. 근거: 입력본 185행. 정정: BM25 점수와 벡터 유사도는 척도가 달라 가중합 전에 정규화하거나 RRF로 순위를 합침. 본인 확인: 시범에서 점수를 합친 방식이 가중합인지 RRF인지는 서류에 없음.

**45. 금융권에서는 검색을 어떤 순서로 붙이는 게 좋다고 보세요?**

> 가진 것으로 먼저 해 보고 부족할 때 하나씩 붙이는 순서가 맞다고 봅니다. 키워드로 풀리는 질문은 Elasticsearch로 최대한 처리하고, 의미 검색이 필요하면 Elasticsearch 안에서 키워드와 벡터를 함께 처리하거나 PostgreSQL에 pgvector를 얹어 쓰며, 같은 질문이 반복돼 응답이 느리면 Redis로 캐시를 붙입니다. PostgreSQL은 자체 전문 검색 기능도 있어 규모가 작으면 키워드와 벡터를 한 DB에서 해결할 수 있는데, 한국어는 형태소 분석 확장을 따로 붙여야 합니다.

- 메모: 통화 21:23, G051. 가이드: 경민은 「금융권은 Elasticsearch로 최대한, 안 되면 PostgreSQL 안 pgvector로 최대한, 느리면 Redis, 그래서 PostgreSQL 하나 붙여 다 쓸 수 있다」고 함. 근거: 경력 사실 없음, 판단. 그 밖에: PostgreSQL 자체 전문 검색은 통화에서 본인이 말한 내용으로, 한국어 형태소 분석 확장이 필요하다는 점을 덧붙임. 정정: Elasticsearch에도 벡터 검색과 하이브리드 검색이 있어 의미 검색을 꼭 PostgreSQL로 옮겨야 하는 것은 아님.

**46. 에이전트 답이 틀리면 책임 문제가 생기는데, 정확도 부담은 어떻게 다루세요? 룰베이스와 에이전트 중 무엇을 고르세요?**

> 답이 정확히 맞아야 하는 일은 룰베이스나 검색 결과를 그대로 보여 주고, LLM은 요약이나 설명처럼 사람이 바로 검토할 수 있는 일에 먼저 씁니다. 에이전트는 확률로 답하니 100%를 기대하기보다, 결과를 검증하는 단계를 서비스 안에 넣어야 합니다. 제 하네스도 에이전트가 끝났다고 해서 끝난 것으로 보지 않고, 완료 기준과 금지 규칙을 모두 통과했는지를 검증 게이트가 판정하게 만들었습니다. 금융 서비스라면 답변마다 근거 문서를 붙이고 근거를 못 찾으면 모른다고 답하게 하는 식으로 같은 원칙을 적용할 수 있습니다.

- 메모: 통화 21:32, G052. 가이드: 「그럴 거면 룰베이스가 속 편하지, 에이전트가 잘못했다가 팀장님한테 깨진다」는 말에 경민이 「그럴 거면 Elasticsearch 쓰지, 빠르고 성능도 낫다」고 함. 근거: 입력본 212행, 213행. 그 밖에: 하네스 사례는 검증 원칙만 잇고 하네스가 RAG와 연결된 것처럼 말하지 않음.

**47. 공고에 LLM과 RAG를 붙이는 일이 있는데, 실무에서 LLM을 어떻게 쓰실 건지 의견을 듣고 싶습니다.**

> LLM 없이 풀리는 곳은 덜 쓰는 게 맞지만, 아예 안 쓰는 건 이 일의 답이 아니고 AI가 들어가야 할 자리는 분명히 넣어야 한다고 봅니다. 키워드 검색, 벡터 검색, 리랭킹으로 근거를 먼저 좁히고, LLM은 그 근거로 답을 만들고 설명하는 마지막 단계에 두는 게 비용과 정확도 양쪽에서 유리합니다. 지금 AI가 들어갈 자리를 없애 버리면 모델이 좋아졌을 때 넣을 곳이 없어 결국 사람이 계속 해야 하니, 덜 쓰더라도 자리는 처음부터 만들어 두는 쪽을 택합니다.

- 메모: 통화 21:18~21:19, G049. 가이드: 「LLM 안 써서 될 거면 덜 쓰는 게 베스트, 안 쓴다는 건 말이 안 되고 AI가 써야 될 부분은 들어가야 한다」는 틀에 경민이 「저희도 실제로 그렇게 말한다」고 했고, 넣을 공간을 만들어 맨 마지막에 넣는 게 저렴하다는 논리를 덧붙임. 근거: 공고 20~24행, 입력본 213행.

### 그래프 DB와 온톨로지

**48. 그래프 DB는 써 보셨어요?**

> 그래프 DB는 써 보지 않았습니다. 대표적인 것이 Neo4j이고, 노드와 관계를 저장해 Cypher라는 질의 언어로 관계를 따라가며 조회한다는 정도로 알고 있습니다.

- 메모: 통화 20:29, G039. 가이드: 경민은 RAG 다음에 「데이터베이스를 뭘 쓸 거냐」, 「그래프 DB를 써 봤냐」가 나올 것이고 그래프 DB는 Neo4j를 많이 쓴다고 함. 근거: 입력본 143행. 그 밖에: 통화에서 본인이 그래프 DB는 잘 모른다고 답해, 안 써 봤다고 먼저 말하게 씀. 「RAG 데이터베이스는 무엇을 쓰시겠어요?」는 「벡터 DB는 무엇으로 구축하나요?」와 같은 질문이라 빼고 그래프 DB만 남김.

**49. 같은 일을 하는데 더 나중에 나온 Neo4j는 왜 안 쓰세요?**

> 질문이 문서 내용을 찾는 수준이면 PostgreSQL로 충분하고, 그래프 DB는 관계를 여러 단계 따라가야 할 때 값을 한다고 보기 때문입니다. Neo4j 질의 자체에는 LLM이 필요 없지만, 문서로 GraphRAG를 만들려면 엔티티와 관계를 뽑는 데 문서마다 LLM 호출이 들어가 비용이 큽니다. PostgreSQL은 사내에 운영 경험이 흔하고 SQL만 알면 유지보수할 수 있어 사람을 구하기도 쉽습니다. 관계 데이터가 조금 있는 정도는 관계 테이블과 재귀 쿼리로 다루고, 관계가 커지면 그때 그래프 DB를 검토하는 순서가 맞다고 봅니다.

- 메모: 통화 20:32~20:33, G042. 가이드: 경민은 「그래프를 타는 순간 LLM 콜이라 돈이 들고, 실무에서 그래프 DB보다 PostgreSQL을 쓴다, RDB도 있고 어디에나 깔려 있고 SQL만 주면 바로 이해하니 안 쓸 이유가 없다」고 답하라고 함. 근거: 입력본 143행. 가이드와 다르게 한 곳: 「실무에서 PostgreSQL을 쓴다」는 서류상 시범 범위라 판단으로 씀. 정정: 그래프 질의 자체에는 LLM이 필요 없고 비용은 그래프 구축과 자연어 질의 변환에서 들며, pgvector는 그래프 DB를 대신하지 않으니 관계 데이터는 관계 테이블과 재귀 쿼리로 구분해 말함.

**50. GraphRAG는 왜 나왔나요?**

> 일반 RAG는 질문과 비슷한 청크를 몇 개 가져오는 방식이라, 여러 문서에 흩어진 관계를 따라가야 하는 질문이나 문서 전체를 아우르는 질문에 약해서 나왔습니다. GraphRAG는 문서에서 엔티티와 관계를 뽑아 그래프로 만들고, 검색할 때 그 관계를 여러 단계 따라가거나 묶음 단위 요약을 써서 답합니다. 예를 들어 「이 특약이 붙을 수 있는 상품과 상품별 보장 제한」처럼 관계를 건너가야 하는 질문에 맞습니다.

- 메모: 통화 20:28, G038. 가이드: 「RAG는 잘못 쌓이면 찾기도, 복구도, 재적재도 어려워 GraphRAG가 나왔다」는 정리에 경민이 「인과관계를 찾기 어려우니 그래프가 나왔다고 볼 수 있다, 보통 그래프 DB라고 한다」고 함. 근거: 경력 사실 없음, 기술 설명. 정정: GraphRAG는 잘못 적재된 데이터를 고치려고 나온 것이 아니라 여러 단계 관계와 전체를 아우르는 질문에 답하려고 나옴.

**51. 온톨로지는 무엇이고, 그래프 DB는 언제 써야 하나요?**

> 온톨로지는 개념과 개념 사이의 관계를 정의한 지식 모델, 곧 스키마이고, 그 구조를 그래프 DB나 RDB에 담아 검색에 씁니다. 그래프 DB는 관계가 많고 여러 단계를 건너야 하며, 같은 말이 쓰는 곳마다 다른 뜻이라 개념 정의가 필요할 때 씁니다. 보험 문서를 10년치 다룬다면 같은 「보험」이라도 상품, 계약, 특약마다 뜻이 달라 온톨로지와 그래프를 들일 만하고, 1년치처럼 범위가 작으면 PostgreSQL의 관계 테이블로도 충분합니다.

- 메모: 통화 20:34, G043. 가이드: 경민은 「온톨로지가 의미상 그래프를 서치하는 방법이고 PostgreSQL로도 제한된 범위에서 된다」며, 「헬스」처럼 뜻이 갈리는 말이 많거나 보험 문서 10년치면 그래프, 1년치면 PostgreSQL이라는 예를 듦. 근거: 경력 사실 없음, 기술 설명. 정정: 온톨로지는 검색 방법이 아니라 개념 사이 관계를 정의한 지식 모델.

**52. 처음부터 그래프 DB로 가지 않는 이유는 뭔가요?**

> 처음에는 관계를 따라가야 하는 질문이 얼마나 되는지 모르니, 검색으로 풀리는지부터 확인하는 게 비용이 덜 듭니다. 다만 나중에 그래프로 옮기려면 엔티티와 관계를 정의하는 모델링이 따로 필요해서, 데이터를 옮겨 넣기만 하면 그래프가 되는 것은 아닙니다. 그래서 처음부터 청크에 문서 ID, 상품, 조항 같은 메타데이터를 붙여 두면 나중에 엔티티를 뽑을 때 출발점이 됩니다.

- 메모: 통화 21:48, G054. 가이드: 경민은 「그래프 DB나 중간에 LLM을 태울 이유가 별로 없고, PostgreSQL에 잘 쌓아 두었다가 Neo4j로 마이그레이션하면 그래프 DB, 시맨틱 그래프가 된다」고 함. 근거: 경력 사실 없음, 판단. 정정: 관계형 데이터를 그래프 DB로 옮기려면 엔티티와 관계를 정의하는 모델링이 필요함.

### 서빙과 경량화

**61. 모델 서빙은 무엇으로 하셨나요? Ollama와 vLLM은 어떻게 다른가요?**

**62. 경량화, 양자화는 해 보셨어요?**

> 양자화는 직접 해 보지 않았고, 원리와 고르는 기준은 알고 있습니다. FP32, FP16, FP8의 숫자는 소수점 자릿수가 아니라 수 하나를 저장하는 비트 수이고, 양자화는 가중치를 INT8이나 INT4처럼 더 적은 비트로 근사해 메모리를 줄이는 것입니다. 8비트는 성능 손실이 작고 4비트 이하로 갈수록 손실이 커지기 때문에, GPU 메모리에 원래 정밀도로 들어가면 그대로 쓰고 안 들어갈 때 8비트, 그다음 4비트 순으로 내려가며 답변 품질을 확인해 고르는 것이 맞다고 봅니다.

### LLM 기본 원리

**63. AI와 머신러닝은 무엇인가요?**

### 비용과 응답 지연

**72. LLM 서비스에서 비용과 정확도는 어떻게 균형을 잡나요?**

> 일의 난이도에 따라 모델과 호출 횟수를 나누는 방식으로 잡습니다. 큰 모델을 쓰거나 여러 번 호출하면 답은 좋아질 수 있지만 비용이 바로 늘어나서, 쉬운 일은 작은 모델에 맡기고 판단이 어려운 일만 큰 모델에 보냅니다. 하네스에서도 작업 성격에 따라 모델을 나눠 쓰는 모델 라우팅을 적용했고, 재시도는 무한히 돌리지 않고 서킷 브레이커로 반복 실패를 끊어 같은 실수에 호출 비용이 계속 나가지 않게 했습니다.

- 메모: 통화 20:35. 가이드: 「LLM은 그래서 항상 돈이랑 찾는 학문이에요」, 호출 단위 과금이라 「콜을 많이 하면 할수록 정확도가 올라가고 좋은데 돈이 많이 든다」. 답변 태도 20:33 「호출하면 돈이 든다」 반영. 근거: 이력서 142행, 147행. 정정: 상용 API 과금은 호출 횟수가 아니라 토큰 수 기준.

**73. 실무에서 LLM 호출을 줄이려는 이유는 무엇인가요?**

> 비용과 응답 시간 두 가지 때문입니다. 상용 API는 입력과 출력 토큰 수만큼, 자체 서빙은 GPU를 쓰는 만큼 비용이 들고, 일반 검색이 수십 밀리초면 끝나는 데 비해 LLM 답변은 몇 초씩 걸립니다. 그래서 규칙과 검색으로 처리되는 것은 LLM 앞에서 끝내고 모델은 마지막 단계에 둡니다. 하네스에서도 빌드, ktlint, Kotlin LSP 검사, 실기기 E2E 결과처럼 정답이 정해진 판정은 스크립트가 하게 하고, LLM 검증 에이전트는 리뷰처럼 규칙만으로 판정하기 어려운 부분에 씁니다.

- 메모: 통화 21:14. 가이드: 「실무상은 AI 안 쓸 수 있으면 안 쓰는 게 베스트예요. 돈 드니까」, 「클로드한테 시키는 거 콜당 돈 받아요」, 검색은 0.0몇 초인데 GPT 같은 모델은 5~7초. 답변 태도 21:07 「호출을 최대한 줄인다」 반영. 근거: 포트폴리오 177행, 이력서 145행. 정정: Claude API는 호출 횟수가 아니라 입력과 출력 토큰 수로 과금. 통화 21:15 본인 발언 「집 맥미니에서 소형 모델이 35초」는 서류에 없고 회사 시범과 섞일 수 있어 안 씀.

## 4. 에이전트, MCP, 프레임워크

### LLM, 에이전트, 하네스

**74. LLM과 에이전트는 어떻게 다른가요?**

> LLM은 입력된 컨텍스트를 받아 다음 토큰을 만들어 내는 모델이고, 호출 사이에 기억이 없습니다. 에이전트는 그 LLM을 루프 안에서 부르면서, 대화 이력과 도구 실행 결과로 매번 컨텍스트를 다시 구성하고, LLM이 고른 도구를 실제로 실행하는 쪽입니다. 그래서 컨텍스트를 이해하는 것은 LLM이고, 무엇을 넣고 무엇을 기억할지 관리하는 것은 에이전트라고 나눠 설명합니다.

- 메모: 통화 20:12, G077. 가이드: 경민은 LLM을 발권 엔진에 비유해 「판정 모델이 아니라 지능, 메모리가 없는 아이」이고 「컨텍스트를 들고 있는 애가 에이전트, 엄밀히 컨텍스트 이해는 LLM」이라고 함. 근거: 경력 사실 없음, 기술 설명.

### MCP와 도구 호출

**78. MCP 도구는 써 보셨죠?**

> 네, 쓰는 것뿐 아니라 SonarQube 조회와 지식베이스 검색 MCP 서버를 Python으로 개발해 팀 하네스에 붙였습니다. MCP 서버는 클라이언트가 tools/list를 요청하면 도구마다 이름, 설명, 입력 JSON Schema를 돌려주고, 모델이 도구를 고르면 클라이언트가 tools/call로 실행을 요청합니다. 그래서 tools.json 같은 고정 파일이 있는 것은 아니고, 모델이 상황에 맞는 도구를 고를 수 있게 설명을 잘 쓰는 것이 중요합니다.

- 메모: 통화 20:42, G079. 가이드: 경민은 「MCP 툴 써 보셨죠?」라며 「툴즈.json」 같은 도구 정의 파일이 존재한다는 건 알지 않냐고 확인. 근거: 입력본 141행, 183행, 198행, 이력서 153행. 정정: tools.json이라는 표준 파일은 없고 서버가 tools/list 응답으로 알림. 그 밖에: 통화에서 「AI가 만들어 준다, 내가 하는 게 있나」로 약하게 답했으나 서류대로 직접 개발로 씀. 사내 MCP로 Jira 등을 연결한 것은 실적으로 넣지 않음. 본인 확인: MCP 클라이언트를 따로 만든 적이 있는지(서류에는 서버만, 클라이언트는 Claude Code).

**79. MCP 도구 호출은 누가 결정하고 누가 실행하나요?**

> 결정은 LLM이 하고 실행은 에이전트 쪽이 합니다. 에이전트가 도구 목록을 컨텍스트에 함께 넘기면 LLM은 쓸 도구와 인자를 출력할 뿐이고, MCP 클라이언트나 에이전트 런타임이 실제로 MCP 서버를 호출해 결과를 다시 컨텍스트에 넣습니다. 실행이 런타임에서 일어나기 때문에, 제 하네스처럼 실행 직전에 훅으로 위험 명령이나 외부 전송을 막는 통제가 가능합니다.

**80. 에이전트가 사내 API를 호출하는 흐름을 설명해 보세요.**

> 사내 REST API를 도구로 감싸 이름, 설명, 입력 파라미터 스키마를 정의해 두면, LLM이 사용자 요청을 보고 그 도구와 인자를 고르고, 런타임이 인증을 붙여 실제 API를 호출합니다. 규정을 먼저 찾아야 하면 검색 도구가 먼저 불리는데, 이때 의미 유사도 계산은 LLM이 아니라 임베딩 모델이 질문을 벡터로 바꾸고 pgvector 같은 벡터 DB가 합니다. 필수 값이 빠졌으면 LLM이 지어내지 않고 사용자에게 되묻도록 멈추게 하고, 호출 권한은 도구 단위로 제한합니다. 제가 만든 SonarQube 조회 MCP 서버도 SonarQube 조회 기능을 이렇게 도구로 감싸 Claude Code가 부르게 한 같은 구조입니다.

- 메모: 통화 20:50~20:52, G086. 가이드: 경민은 원스토어 앱 등록 API를 가정해 「LLM이 규정집 벡터를 PostgreSQL에서 의미 유사도로 찾고 PDF를 메모리에 올려 읽은 뒤, curl 값을 조합해 빠진 스레드 ID와 날짜를 되묻는다」는 흐름을 설명. 근거: 입력본 141행. 정정: 의미 유사도 검색은 LLM이 아니라 임베딩 모델과 벡터 DB가 하고 LLM은 검색을 요청하고 결과를 읽음. 그 밖에: 앱 등록 API 예는 경민의 가정이라 경험으로 쓰지 않고 흐름만 살림.

**81. 검색 저장소는 어떻게 구성하고, 조회는 누가 하나요?**

> 조회는 모델이 아니라 에이전트의 검색 코드가 하고, 모델은 그 결과를 컨텍스트로 받아 읽기만 합니다. 저장소는 문서가 적으면 폴더와 목록 파일로도 되고, 많아지면 PostgreSQL과 pgvector에 벡터와 메타데이터를 같이 두고, 관계가 복잡하면 그래프 DB를 둡니다. 제 하네스에서 코드 리뷰 때 Kotlin LSP로 호출 관계를 추적하는 것도 같은 구조로, 탐색 도구는 런타임이 실행하고 모델은 결과만 받습니다.

- 메모: 통화 20:46~20:47, G084. 가이드: 경민은 저장소를 폴더, JSON 인덱스, PostgreSQL, 그래프 DB로 나누고 「실행 로직은 다 에이전트, 임베딩 조회도 에이전트」라는 정리에 동의했으며, 코드를 텍스트, 인덱싱, 코드맵으로 탐색하는 방식을 갖춰 주는 게 「하네스」라고 함. 근거: 포트폴리오 93행, 176행. 정정: 저장소 조회는 모델이 아니라 에이전트, 곧 검색 코드가 함. 본인 확인: 통화에서 말한 코드맵 인덱싱은 서류에 없어 서류의 Kotlin LSP 호출 관계 추적으로 씀. 하네스의 코드 탐색은 RAG가 아님.

### 에이전트 프레임워크

**82. LangGraph나 LangChain 써 보셨어요? OpenAI나 Google ADK는요?**

> LangGraph, LangChain, Google ADK, OpenAI Agents SDK 모두 써 보지 않았습니다. 이것들은 모델 연결, 도구 호출, 상태 관리를 코드로 짜게 해 주는 에이전트 프레임워크로, 서비스에 들어가는 에이전트를 직접 만들 때 씁니다. 제 에이전트 경험은 Claude Code를 실행 환경으로 쓰고 그 위에 역할별 에이전트, 스킬, 훅, MCP 서버를 얹은 쪽이라, 도구 정의와 사람 확인 지점을 설계하는 원리는 같지만, 상태 저장은 워크플로 단계 수준에서만 해 봤고 흐름과 상태를 코드로 짜는 부분은 다릅니다.

- 메모: 통화 20:54, G087. 가이드: 경민은 에이전트 쪽 첫 질문이 「랭그래프 써 봤어요? 랭체인 써 봤어요?」이고, 「랭그래프 써 봤어요, 그거보다 옛날이면 랭체인 써 봤어요」라고 답하는 예를 들며 「저 RAG 써 봤어요」라고 하면 질문 지점에 안 맞는다고 함. 근거: 이력서 140~156행. 가이드와 다르게 한 곳: 서류에 LangGraph, LangChain 사용이 없어 안 써 봤다고 먼저 말하고, 질문 지점인 에이전트 개발 도구에 맞춰 Claude Code 하네스로 이음. 정정: Google 것은 ADK, OpenAI 것은 Agents SDK가 이름.

**83. 서비스형 에이전트를 새로 만든다면 무엇으로 짜시겠어요?**

> LangGraph를 먼저 검토하겠습니다. 서비스형 에이전트는 상태 저장과 재시도, 사람 확인 대기를 코드로 다뤄야 하는데, LangGraph가 이런 흐름을 그래프로 짜는 데 맞춰져 있기 때문입니다. 다만 직접 써 본 적은 없어서, 작은 흐름 하나를 먼저 짜 보고 요구에 맞는지 확인한 뒤 정하겠습니다.

- 메모: 통화 20:57, G089. 가이드: 「해 봤다고 하지 않고 LangGraph 붙일까 고민해 봤다고 대답하면 되겠다」는 말과 「에이전트 개발을 뭘로 했냐, 그냥 LangGraph로 했다, LangChain으로 했다」는 말이 섞여 나옴(화자 확정 안 됨). 근거: 경력 사실 없음, 판단, 이력서 140~156행에 LangGraph 사용 없음. 가이드와 다르게 한 곳: 「에이전트 개발을 뭘로 했냐」는 G023 질문과 합쳐 그쪽에서 Claude Code 하네스로 답하고, 여기에는 LangGraph 꼬리만 남김. 「LangGraph로 했다」, 「붙일까 고민해 봤다」는 서류에 없어 앞으로의 판단으로 씀.

**84. LangChain과 LangGraph는 무엇이고, 이런 SDK가 왜 필요한가요?**

> 둘 다 LangChain이라는 회사가 만든 오픈소스입니다. LangChain은 모델 연동, 프롬프트 템플릿, 검색기, 도구 연결 같은 부품을 모아 둔 라이브러리이고, LangGraph는 상태와 분기, 반복을 그래프로 짜는 에이전트 프레임워크로 LangChain 부품과 함께 쓸 수 있습니다. 필요한 이유는 모델 제공사마다 API 규격이 조금씩 다르고 벡터 DB, 캐시, 파일 연결도 매번 짜야 하는데, 이런 어댑터를 공통 인터페이스로 묶어 주기 때문입니다. 안드로이드로 치면 Jetpack 라이브러리처럼 반복되는 연결 코드를 맡아 주는 역할이라고 이해하고 있습니다.

- 메모: 통화 20:48~20:49, G085. 가이드: 경민은 둘을 「같은 재단 프로그램」, 「에이전트의 자바 스프링」, 「안드로이드 SDK 같은 존재」라 하고, LangChain이 프롬프트를 재조립한다는 말에 「재조립이 어댑터」라고 함. 근거: 경력 사실 없음, 기술 설명. 정정: 재단이 아니라 LangChain Inc.가 만든 오픈소스이고, LangChain에는 프롬프트 템플릿으로 프롬프트를 조립하는 기능이 실제로 있음.

**85. LangChain과 LangGraph는 무엇이 다른가요?**

> LangChain은 정해진 순서로 흐르는 체인을 짜는 데 맞고, LangGraph는 노드와 엣지로 상태를 들고 분기하거나 앞 단계로 되돌아가는 흐름을 짜는 데 맞습니다. LangGraph는 LangChain의 새 이름이 아니라 같은 회사가 따로 낸 라이브러리이고, 둘 다 지금도 쓰입니다. 재시도, 사람 확인 대기, 중간 상태 저장이 필요한 에이전트는 LangGraph 쪽이 자연스럽습니다.

- 메모: 통화 20:55~20:56, G088. 가이드: 경민은 「기능은 똑같고 LangChain은 끝이 있는 플로우, LangGraph는 되돌아가기가 되며, 옛날 게 LangChain, 요즘 게 LangGraph이고 재시도 루프 때문에 이름을 바꿨다」고 하며 ReAct와 리랭킹을 재시도 예로 듦. 근거: 경력 사실 없음, 기술 설명. 정정: LangGraph는 새 이름이 아니라 별도 라이브러리이고, ReAct는 추론과 도구 실행을 번갈아 하는 에이전트 패턴, 리랭킹은 검색 결과 순서를 다시 매기는 단계라 둘 다 재시도 기법이 아님.

**86. LangGraph로 에이전트를 짠다면 어떻게 구성하시겠어요?**

> 직접 써 보지는 않았지만, 핵심은 상태와 노드, 엣지를 정하는 것입니다. 대화 이력과 검색 결과를 담는 상태를 정의하고, 질문을 임베딩해 벡터 DB에서 찾는 검색 노드와 LLM을 부르는 생성 노드를 두고, 검색 결과가 부족하면 검색으로 되돌아가는 조건 엣지를 겁니다. 시스템 프롬프트는 생성 노드의 고정 지침으로 두고, 사용자 입력과 검색 결과는 상태에서 꺼내 메시지로 넣으며, 상태는 체크포인터로 DB에 저장해 끊겨도 이어 가게 합니다.

- 메모: 통화 20:57, G090. 가이드: 경민은 「LLM 어떻게 붙여? RAG 어떻게 붙여? 임베딩 서치 어떻게 해? 시스템 프롬프트와 사용자 입력은 어디다 써?」만 물으면 LangGraph 기능은 끝이고 나머지는 회사별 어댑터라고 함. 근거: 경력 사실 없음, 기술 설명. 그 밖에: 안 써 본 도구라 「직접 써 보지는 않았지만」으로 시작.

**87. ADK와 SDK는 어떻게 다른가요?**

> SDK는 어떤 플랫폼을 쓰기 위한 개발 도구 묶음을 두루 부르는 말이고, ADK는 Google이 낸 Agent Development Kit라는 제품 이름입니다. 그래서 LangGraph까지 ADK라고 묶어 부르기보다, LangGraph, Google ADK, OpenAI Agents SDK를 통틀어 에이전트 프레임워크라고 부르는 것이 정확합니다.

- 메모: 통화 20:59, G092. 가이드: 경민은 「LangGraph는 ADK 중 하나이고 작년만 해도 SDK와 ADK를 구분하지 않았다, 회사마다 다 있다」고 함. 근거: 경력 사실 없음, 기술 설명. 정정: ADK는 Google 제품 이름이고, 묶어 부를 때는 에이전트 프레임워크.

### 상태, 재시도, 사람 개입

**88. 에이전트의 재시도와 사람 개입은 어떻게 구현하나요?**

> 상태를 저장하는 상태 머신으로 짜고, 재시도에는 횟수 상한 같은 멈출 조건을, 사람 확인이 필요한 지점에는 인터럽트를 겁니다. LangGraph에는 실행을 멈추고 사람 입력을 기다렸다가 이어 가는 인터럽트 기능이 있고, 이렇게 필요한 지점에서만 사람이 끼어드는 것을 Human-in-the-loop, 줄여서 HITL이라고 부릅니다. 제 하네스에도 같은 원리를 넣었는데, 같은 실패가 반복되면 서킷 브레이커로 멈추고, 단계마다 상태를 저장해 끊긴 단계부터 재개하며, 계획과 최종 소스는 사람이 보고 금지 규칙을 어겨야 하는 상황이면 에이전트가 멈추고 사람에게 묻습니다.

- 메모: 통화 20:58, G091. 가이드: 경민 회사는 「스테이트머신에 상태값을 다 넣어 리트라이하고 while 루프에 브레이크 포인트를 걸며, 사람에게 물어야 할 때 인터럽트로 멈추는 게 HITL이고 LangGraph에 있다」고 함(경민 사례). 근거: 이력서 147행, 포트폴리오 105행, 151행. 그 밖에: 통화의 「MCP도 그렇게 했던 것 같다」는 뜻이 원문에서 불명해 넣지 않음.

**89. 에이전트에 대화 이력 저장이 왜 필요한가요?**

> LLM은 호출 사이에 기억이 없어서, 이력을 저장해 두지 않으면 세션을 껐다 켜거나 사람에게 질문을 넘긴 뒤 돌아왔을 때 왜 그 값을 물었는지 잃어버립니다. 그래서 세션 ID 기준으로 대화 이력과 진행 상태를 RDB 같은 저장소에 두고, 다시 시작할 때 불러와 컨텍스트를 복원합니다. LangGraph라면 체크포인터를 PostgreSQL에 붙이는 방식입니다. 제 하네스에서는 워크플로 단계 상태를 Jira 일감 코멘트와 단계별 저장으로 남겨 진행이 끊겨도 그 단계부터 이어 가게 했는데, 대화 이력 자체를 저장하는 것과는 층위가 다릅니다.

- 메모: 통화 21:34, G094. 가이드: 경민은 「에이전트는 LangGraph든 뭐든 RDB가 필요할 수 있다, 채팅 이력이 있어야 세션을 꺼도 기억이 돌아오고 없으면 왜 파라미터를 요청했는지 기억 못한다」고 함. 근거: 포트폴리오 105행, 144행. 그 밖에: 시범에서 채팅 이력을 RDB에 쌓았다는 것은 서류에 없어 원리로만 말함.

### 챗 에이전트와 시스템 구성

**90. 만드신 시스템의 구성을 에이전트, 모델, 서빙, 저장소로 나눠 설명해 주세요.**

> 서로 연결하지 않은 두 구성이 있어서, 팀 하네스 기준으로 말씀드리겠습니다. 팀 하네스는 에이전트가 Claude Code이고 모델은 Claude이며, Claude는 가중치를 공개하지 않는 상용 모델이라 서빙은 제가 직접 하지 않습니다. 지식은 룰과 레퍼런스 문서, 앱 저장소마다 둔 프로젝트 정보로 둡니다. 사내 장비에서 서빙까지 직접 구성한 것은 앞서 말씀드린 RAG 시범이 따로 있습니다.

**91. 챗 에이전트에는 어떤 기능을 넣으셨어요? 넣는다면 무엇을 넣으시겠어요?**

**92. 에이전트 빌더 플랫폼은 어떻게 동작하나요?**

> 에이전트를 코드로 짜지 않고 화면에서 구성해 배포하게 해 주는 플랫폼입니다. 화면에서 프롬프트, 쓸 모델, 도구, 지식 문서를 고르고 흐름을 배치하면, 플랫폼이 문서를 인덱싱해 RAG로 붙이고 에이전트를 API나 채팅 화면으로 배포해 줍니다. 저는 이런 빌더를 써 보지는 않았고, 비슷하게 룰, 스킬, 에이전트를 플러그인으로 묶어 팀원이 설치만 하면 같은 환경을 쓰게 한 경험이 있습니다.

### 지원 직무를 어떻게 이해했나
